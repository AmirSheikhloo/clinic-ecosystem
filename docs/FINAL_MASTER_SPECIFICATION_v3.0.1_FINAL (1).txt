## 00. Purpose and authority of this document

1. This document is the integrated, content-frozen v3.0 architecture and implementation specification for the Clinic Management Ecosystem, with the narrow execution clarifications recorded in v3.0.1. Its explicit Open Items and four authorization gates are deployment, implementation-evidence, provider and legal/commercial controls; they do not mean that required document chapters or the architecture baseline are still being drafted. Production remains blocked until Gate D is approved.
2. It combines the v1.3 baseline with the documented v3.0 Architecture Change Records, amendments, new clauses and explicit Open Items.
3. It is not a brainstorming document and must not be treated as a suggestion list.
4. Implementers must follow the accepted v1.3 baseline. Gate A authorizes only isolated development, schema/migration work, local tests and Testcontainers verification for v3.0 extensions when the product owner explicitly starts that work. It does not authorize production deployment, live patient data, live payment processing or customer-facing activation. Those require the relevant Gates B, C and D.
5. A proposed architectural change requires an explicit Architecture Change Record and must not be silently introduced through code.
6. The legacy system is a migration source and reference; it is not the architectural authority.
7. The new architecture takes precedence over legacy database structure, legacy endpoints, legacy UI structure and legacy implementation shortcuts.
8. The v1.3 Integration Test Foundation is CLOSED and must not be reopened merely for theoretical perfectionism; v3.0 features add tests without weakening the foundation.
9. The v1.3 ScheduleAppointmentHandler baseline is accepted; the v3.0 multi-resource/dual-pool extension requires the new concurrency and failure tests stated in Section 53.
10. When the product owner chooses to begin engineering, the next technical phase is Gate A: repository/module structure, database boundaries, additive schema migrations and acceptance tests in development/Testcontainers. This clause grants no instruction to begin coding now. Production authorization follows only after the applicable Gates A–D are closed.

# 02. Architecture principles

36. PostgreSQL is the operational persistence technology for both Local Hub and Cloud Hub.
37. SQLite is NOT the backend operational source of truth.
38. Tauri may use SQLite only as a client-side queue/cache/transport mechanism.
39. Client-side SQLite must never become the authoritative clinic database.
40. Client-side SQLite must not independently implement business truth that contradicts Local Hub.
41. Critical business invariants belong in the domain/application layer and, where possible, in PostgreSQL constraints.
42. Application-level locks are not a substitute for PostgreSQL transactional guarantees.
43. Timestamp ordering is not the authoritative distributed ordering mechanism.
44. Sequence-based ordering is required for synchronization streams.
45. UUIDv7 is the application-level identifier strategy.
46. UUIDs must not be generated by the database as a substitute for the application-level UUIDv7 policy.
47. HLC is rejected as unnecessary complexity for the current system.
48. Last-Write-Wins is rejected as a general conflict-resolution strategy.
49. Blind automatic retries are rejected for optimistic-concurrency conflicts.
50. Sync is not backup.
51. Replication is not backup.
52. A successful HTTP response is not by itself proof that durable business state exists.
53. Every business mutation must have a clearly defined transaction boundary.
54. Domain Events, Integration Events and Sync Messages are distinct concepts and must not be conflated.

### v3.0 RBAC scope extension to clauses 78–88

Tenant roles include `CLINIC_OWNER`, `CLINIC_MANAGER`, `DEPUTY_ADMIN`, `RECEPTIONIST`, and explicitly granted operational roles. `SUPER_ADMIN` belongs to the SaaS Control Plane and is not a tenant role. `CLINIC_OWNER` and `CLINIC_MANAGER` permissions are distinct and must be represented in server-side permission assignments, not inferred from UI labels. Doctors and specialists may exist as `staff_profiles` without a software login; in the initial product scope, clinical providers do not receive panel access by default. Any later provider login requires an explicit user account and permissions. A receptionist may enter appointments, patient operational notes and authorized financial facts, but may not perform manager-only configuration, exports, or privileged financial approval unless the corresponding permission is explicitly granted. `DEPUTY_ADMIN` permissions must be individually scoped and audited.

# 06. Local Hub and Cloud Hub

89. Local Hub is a FastAPI + PostgreSQL system.
90. Cloud Hub is a FastAPI + PostgreSQL system.
91. They may have different schemas where appropriate.
92. Local and Cloud schemas do not have to be identical.
93. Synchronization is an integration protocol, not database replication.
94. Local Hub is the primary operational source of truth for physical clinic activity.
95. This includes physical reception operations, in-clinic presence and payments performed at the clinic.
96. Cloud Hub is authoritative for the service/catalog policy.
97. Cloud Hub is authoritative for RBAC policy.
98. Cloud Hub is authoritative for online reservation commands originating from cloud-connected external channels.
99. The authority split is per business capability/context, not a license to write the same business record independently on both sides without a conflict protocol.
100. Every cross-hub entity must have an explicit ownership/authority rule.
101. An implementation must not assume that a record is simultaneously authoritative in both databases.
102. Local physical operations must be represented in synchronization events that Cloud Hub can consume where cloud visibility is required.
103. Cloud-originated online reservations must be represented locally through Integration Events.
104. Cross-hub appointment collisions must never be silently resolved by LWW.

107. The PostgreSQL EXCLUDE constraint remains the final local invariant for appointments stored in a given hub.

109. The authority map must be encoded in the application layer and tested.

### v3.0 authority and dual-pool amendment to clauses 98–109

Cloud Hub is authoritative for `ONLINE` appointments originating from the clinic website and clinic bot. Those channels share one online capacity pool. Local Hub is authoritative for in-clinic physical reception operations and `MANUAL` appointments entered by authorized staff. A Local Hub MANUAL appointment remains MANUAL after synchronization and must never be reclassified as ONLINE. MANUAL appointments may intentionally overlap with ONLINE and other MANUAL appointments; such conflicts are not auto-resolved, deleted, or used to cancel an ONLINE booking. Cloud read models must preserve the collision signal and expose it to authorized clinic staff. This policy deliberately accepts that an offline local MANUAL entry cannot acquire a distributed lock over Cloud ONLINE capacity. The system must disclose and surface this conflict rather than claiming globally collision-free scheduling. Cloud ONLINE creation must still be serialized by its authoritative PostgreSQL constraints. The website and bot may not independently maintain appointment capacity pools.

# 07. Appointment model and concurrency

110. Appointment overlap is a database-enforced invariant.
111. PostgreSQL must use an EXCLUDE USING gist constraint for the relevant resource/time-slot rule.
112. The v3.0 canonical overlap rule is based on `appointment_resource_allocations`: `tenant_id WITH =`, `resource_id WITH =`, and `time_slot WITH &&`, restricted to the ONLINE pool and capacity-occupying allocation states. The historical single `room_id` design is superseded. `btree_gist` remains mandatory. The SQL contract appears in Section 53.
113. `time_slot` uses `tstzrange`.
114. The `btree_gist` extension is required.
115. Application checks may provide early feedback but are not the final concurrency guarantee.
116. The database constraint is authoritative for same-database overlap.
117. ScheduleAppointment must flush before interpreting the resulting IntegrityError.
118. A violation of `no_overlapping_appointments` is translated to the domain/application CapacityConflictException.
119. The conflicting transaction must not corrupt the successful appointment.
120. The transaction must recover correctly after the IntegrityError.
121. Appointment mutations must use the UoW transaction.
122. Appointment state transitions must be explicitly validated.
123. An appointment cannot be changed through an endpoint that bypasses authorization, versioning, idempotency and audit requirements.
124. Authorized MANUAL staff booking is an explicit business capability: receptionists/managers may create overlapping MANUAL appointments without consuming or blocking ONLINE capacity. Such overbooking must be visible, acknowledged and audited as defined in Section 53; it is not an override of the ONLINE exclusion constraint.
125. MANUAL overbooking must never disable, bypass or weaken the PostgreSQL constraint protecting concurrent ONLINE allocations. All MANUAL overlap acknowledgements require the dedicated permission and server-side audit record defined in Section 53.

# 08. Optimistic concurrency

126. Mutable aggregates use `aggregate_version`.
127. A successful aggregate mutation increments the version according to the aggregate contract.
128. Clients use `If-Match`/expected-version semantics for protected mutations.
129. A version mismatch must roll back the attempted mutation.
130. The API returns RFC7807-compatible `412 Precondition Failed`.
131. The server must not silently merge incompatible changes.
132. Blind automatic retries are forbidden for optimistic-concurrency failures.
133. Create operations do not require a previous version.
134. Sync processing must not confuse aggregate version with global message sequence.
135. Aggregate version answers "which version of this aggregate?".
136. Sequence answers "where is this message in the sync stream?".
137. These two ordering dimensions must remain separate.

# 11. Transaction and Unit of Work

161. A business mutation uses one explicit UoW transaction.
162. The UoW contains the business mutation.
163. Domain events produced by that mutation are persisted within the same transaction.
164. Outbox records are staged within the same transaction.
165. If any required part fails, the transaction rolls back.
166. No external network call is required to commit a local business transaction.
167. External delivery is asynchronous through Outbox processing.
168. Commit is the durable boundary for the local transaction.
169. The implementation must not publish a sync message externally before the local transaction has durably committed.
170. The accepted ScheduleAppointmentHandler follows this pattern.

# 12. Idempotency

171. Idempotency identity is:
   `principal_id + operation_scope + idempotency_key`.
172. Request fingerprinting is mandatory where the endpoint contract requires it.
173. RFC8785 JSON Canonicalization Scheme is used for canonical JSON representation.
174. The fingerprint prevents the same key from being reused for a different request.
175. A repeated request with the same identity and same fingerprint may replay the cached successful response.
176. A repeated request with the same key but a different fingerprint must fail with an idempotency conflict.
177. Concurrent requests using the same idempotency identity must never execute business logic twice.
178. One request may own the IN_PROGRESS state.
179. A concurrent request encountering an active owner receives `425 Too Early` according to the frozen contract.
180. A completed request returns the cached result.
181. A failed transaction must not leave a false COMPLETED record.
182. Idempotency state changes must be transactional with the business operation.
183. Bot commands use the same idempotency model.
184. Future integrations such as Nobat.ir use the same model.

# 13. ScheduleAppointmentHandler contract

185. Command fields include correlation_id, idempotency_key, request_fingerprint, principal_id, actor, patient_id, service_id, booking_channel, capacity_pool, requested resource-allocation set, start_time and end_time. A singular `resource_id` is insufficient for multi-resource services.
186. The handler opens the UoW.
187. It claims idempotency before performing the business mutation.
188. COMPLETED returns the cached appointment identifier.
189. An active competing idempotency owner produces the defined `425 Too Early` behavior.
190. A fingerprint mismatch produces the defined conflict.
191. Appointment.schedule validates domain rules.
192. The appointment is added through the repository.
193. The transaction flushes before handling the PostgreSQL overlap error.
194. `no_overlapping_appointments` is translated into CapacityConflictException.
195. The handler publishes domain events to the Outbox staging area.
196. The idempotency record is marked COMPLETED with the response.
197. The transaction commits.
198. The handler returns the appointment identifier/result.
199. Integration tests verify exactly one appointment, exactly one relevant Outbox message and a COMPLETED idempotency record.
200. Replay tests verify the same result without duplicate business state.
201. Real concurrency tests are part of the implementation/testing phase.

### v3.0 ScheduleAppointmentHandler amendment to clauses 185–201

Before persistence, the handler resolves all mandatory `service_resource_requirements`, validates the requested resource set and applies a consistent lock order. For ONLINE requests it first expires only overlapping expired holds that could conflict with the requested resources/time range, then inserts the appointment and all required allocation rows in one UoW. The database EXCLUDE constraint remains the final authority. For MANUAL requests, the handler queries overlapping ONLINE and MANUAL appointments, returns the exact conflicts for display, and requires explicit `acknowledge_overlap = true` plus `ALLOW_MANUAL_OVERBOOKING` permission before committing the intentional overlap. The manual confirmation audit snapshot is committed in the same UoW. A manual booking must never be reclassified as online during synchronization.

# 14. Domain Events, Integration Events and Sync Messages

202. A Domain Event describes a meaningful change inside the domain.
203. An Integration Event is a deliberately designed external contract derived from approved domain facts.
204. A Sync Message is the transport envelope carrying an Integration Event between hubs.
205. A Domain Event is not automatically a public Sync Message.
206. PII must not leak simply because an internal event contains it.
207. Only approved Integration Event schemas may cross hub boundaries.
208. PII fields must be explicitly minimized/filtered.
209. Integration events must be versionable.
210. Consumers must tolerate duplicate delivery.
211. Consumers must not infer business truth from arbitrary database CRUD replication.
212. CRUD replication is rejected as the synchronization architecture.

# 15. Outbox

213. Every eligible integration event is staged through Outbox.
214. Outbox rows are durable before delivery begins.
215. Delivery uses a lease-based two-phase mechanism.
216. TX1 claims messages and sets `locked_until` and `lease_id`, then commits.
217. TX2 performs network delivery.
218. ACK uses a conditional update such as:
   `WHERE message_id = X AND lease_id = Y`.
219. A stale worker must not ACK a message after its lease has been replaced.
220. Expired leases can be reclaimed.
221. Duplicate delivery is expected.
222. Delivery workers must be safe under process crash/restart.
223. Shutdown must allow in-flight work to finish until the configured graceful-shutdown deadline, after which leases become recoverable.
224. Outbox is not a substitute for a backup.

# 16. Inbox

225. Incoming Sync Messages are processed through Inbox semantics.
226. Inbox records provide duplicate-delivery protection.
227. Integration handling and Inbox COMPLETED state are committed in the same DB transaction.
228. If the handler rolls back, Inbox must not falsely indicate successful processing.

# 17. Sync API

232. Business API and Sync API are separate surfaces.
233. Push endpoint:
   `POST /sync/v1/messages/push`.
234. Push body is a JSON array of Sync Messages.
235. Push authentication uses Ed25519 signatures.
236. Push signing input is:
   `timestamp UTC Z + node_id + RAW_HTTP_BODY_BYTES`.
237. The signature is computed over the exact raw HTTP body bytes.
238. Pull endpoint:
   `GET /sync/v1/messages/pull?after_sequence={N}`.
239. Pull signing input includes timestamp, node_id, HTTP method, canonical path and canonical RFC3986 query.
240. Query canonicalization must be deterministic.
241. Base64URL is used without padding.
242. Replay protection uses a five-minute timestamp window according to the frozen contract.
243. Node identity is cryptographically bound to the relevant key.
244. Revoked nodes/keys must be rejected.
245. Sync authentication is independent from human JWT authentication.

# 18. Cryptography and authentication

246. JWT signing uses RS256 or ES256 according to the deployed key policy.

### v3.0 node licensing extension to clauses 243–257

Cloud-signed `LicenseLeaseToken` is a separate entitlement artifact from the Sync authentication signature. It is signed with Ed25519 and bound to `tenant_id`, `node_id`, a unique `lease_id`, monotonic `lease_sequence`, `issued_at_utc`, `not_before_utc`, `expires_at_utc`, `grace_period_ends_at_utc`, `allowed_modules`, `feature_entitlements`, `max_lan_client_seats`, `minimum_supported_app_version` and `signing_key_id`. Local monotonic counters deter ordinary clock rollback and casual replay but cannot prevent restoration of a full disk image. The decommission flow is defined in Section 56.

# 26. Backup, disaster recovery, RPO and RTO

318. Sync is not a backup mechanism.

322. Streaming replication is a future HA option, not a replacement for backup.

326. Backup freshness must be monitored.

328. RTO target is a maximum of one hour for restoration of the defined complete system onto a replacement server.

331. At least one recovery copy must be isolated from the primary failure domain.
332. Restore verification must be performed periodically.
333. A backup that has never been successfully restored is not considered proven.
334. Backup/restore procedures must be documented and executable by the responsible operator.

### v3.0 Cloud/SaaS DR extension to clauses 318–334

The v1.3 `RPO <= 5 minutes` and `RTO <= 1 hour` targets remain scoped to the defined Local Hub disaster scenario only. They must not be generalized to Cloud Hub, SaaS Control Plane, Object Storage or KMS without separate measurable objectives and load-tested restore evidence. A separate full-platform DR plan must cover Control Plane, tenant databases, Object Storage, configuration/recovery metadata, and key recovery. Super Admin may initiate encrypted scheduled or manual platform backups under MFA and audit, but backup capability does not grant ordinary permission to browse patient content. All restore paths must enforce the independent tenant-erasure tombstone registry before reopening traffic. See Section 56.

# 50. Operational Clinic Accounting, Revenue Sharing & Reporting Contract

692. The financial subsystem is an **Operational Clinic Billing, Cashier, Insurance-Tracking and Revenue-Sharing Ledger** sized for clinic operations. It must be capable, auditable and reportable without becoming a general-purpose ERP.
693. The initial scope does **not** include general-ledger double-entry bookkeeping, chart of accounts, journal vouchers, trial balance, payroll, salary calculation, tax filing or a claim of statutory e-invoicing compliance. A later requirement for any of these needs a separate explicit scope decision.
694. Financial facts must be represented as distinct concepts: service delivery, invoice and invoice line, actual money receipt, prepayment/credit, allocation of money to an invoice, refund, financial adjustment, insurer-expected amount/settlement, and revenue-share allocation. These concepts must not be collapsed into one mutable `balance` field.
695. `ServiceRecord` means that a service was performed or otherwise operationally recorded; `InvoiceItem` means a charge line. They are related but not interchangeable. The model must explicitly represent the relationship, including an approved charge that has no performed-service record where a genuine business rule requires one.
696. An invoice/charge may be editable only while in a non-posted draft state. Once posted, its financial facts and pricing snapshots must not be silently edited or deleted; corrections must use explicit adjustment, credit-note, cancellation or refund records appropriate to the case.
697. At posting, each invoice line must snapshot the service identity/code/name, quantity, unit tariff, pricing-rule version, relevant payer/allocation policy version and the final amounts used. Later catalog or tariff changes must not rewrite historical invoices or reports.
698. Use distinct integer-IRR fields for `gross_service_amount`, `discount_amount`, `subsidy_amount`, `rounding_reduction_amount`, `rounding_surcharge_amount`, `basic_insurance_expected_share`, `supplementary_insurance_expected_share` and `patient_payable_amount`. Amounts that represent reductions must be non-negative; an upward rounding charge must be represented separately rather than hidden as a negative discount.
699. The displayed aggregate «رایگان/تخفیف» is derived, never stored as a replacement for its underlying fields. For this contract, its report formula is `discount_amount + subsidy_amount + rounding_reduction_amount`. `rounding_reduction_amount` means only the reduction from rounding down; an upward rounding charge is kept in `rounding_surcharge_amount` and is not counted as free/discount. A fully free service may be represented as a full discount with an explicit reason code. Components must never be counted twice.
700. A versioned pricing/allocation policy must define the order in which tariff, discounts, subsidy, rounding and insurer/patient responsibility are calculated. Unless an explicitly named and auditable adjustment applies, `net_chargeable_amount = gross_service_amount - discount_amount - subsidy_amount - rounding_reduction_amount + rounding_surcharge_amount`, and `net_chargeable_amount = basic_insurance_expected_share + supplementary_insurance_expected_share + patient_payable_amount`. Both identities must be tested; an unexplained imbalance is forbidden.
701. Manual discounts, subsidies, free services and rounding reductions must capture the acting user, timestamp, reason/code and any required approver. Authorization/approval thresholds must be enforced server-side; hiding a UI action is not sufficient.
702. Expected insurance shares represent an amount attributed to an insurer, **not cash received**. Actual insurer remittance/settlement must be represented separately and reconciled with the relevant expected amount; an expected insurance share must never be counted in a cashier collection report as if payment had already arrived.
703. Patient responsibility, insurer responsibility, actual receipts, refunds, outstanding patient debt and unapplied patient credit must remain separately queryable. A patient's debt report must not mistakenly count an amount expected from an insurer as patient debt.
704. Invoice numbers and payment-receipt numbers are distinct human-readable identifiers; neither replaces the immutable UUIDv7 primary key. Refunds may have their own human-readable number where useful for print/search.
705. Human-readable numbers must be assigned server-side with a concurrency-safe mechanism and unique scope (at minimum clinic plus document type/number). They must be immutable once issued. Gaps may occur; the system must not promise gapless numbering unless a separately verified legal/business requirement requires it. Internal numbering must not be represented as proof of statutory tax-invoice compliance.
706. `PaymentReceipt` records an actual, confirmed inflow of money. A failed/pending payment attempt is not a posted receipt. Each receipt must preserve amount, currency, receipt timestamp, payer/source, operator, payment instrument and applicable allocations.

**706.1 — PaymentAttempt, UnverifiedPaymentClaim and PaymentReceipt are separate facts.** Starting a gateway redirect or creating a payment link creates a `PaymentAttempt`, not a receipt. A card-to-card claim, screenshot or unverified external payment reference creates an `UnverifiedPaymentClaim` and is excluded from collection reports. A `PaymentReceipt` may be posted only after the following method-specific requirements are satisfied:

- **`CASH`:** record amount/currency, receipt timestamp, `operator_user_id`, actor/audit context and `shift_id`/cashier session. Record a managed cash-drawer/register reference when the clinic uses one. The operator must hold `RECORD_VERIFIED_FINANCIAL_RECEIPT`. A bank destination account or bank transfer reference is not required solely for a CASH receipt.
- **`POS`:** record managed `pos_terminal_id`, terminal/provider reference or batch/trace identifier when supplied, amount/currency, timestamp, operator and cashier shift. The POS terminal must belong to the tenant and be active/managed. Record the terminal's actual authorization/settlement state; do not label a merely authorized transaction as settled unless the provider/terminal state supports that claim.
- **`CARD_TO_CARD`:** record the bank trace/reference identifier, destination account/card reference belonging to the clinic, amount/currency, timestamp and operator. Verification requires a trustworthy bank/account statement or approved bank-reconciliation evidence that confirms the inflow. An uploaded screenshot alone remains an `UnverifiedPaymentClaim`.
- **`ONLINE`:** require server-to-server gateway verification matching expected merchant ID, order/PaymentAttempt ID, amount, currency, successful settlement status and unique provider transaction/reference. Verify webhook signature where applicable, enforce callback idempotency and reconcile ambiguous timeouts before posting a receipt.

All methods require the explicit relevant permission and immutable audit attribution. A receptionist cannot promote an unverified claim by a simple status toggle.
707. The initial payment-method vocabulary is `CASH`, `POS`, `CARD_TO_CARD` and `ONLINE`, with any additional method introduced only through an explicit typed extension. `pos_terminal_id` is required for `POS` and must refer to a managed terminal record; it is not free-form text. A POS terminal can be associated with its relevant clinic/location and settlement account/reference where operationally needed.

**707.1 — Direct clinic gateway (BYO Merchant).** Each tenant configures its own supported payment gateway credentials, encrypted at rest with the tenant's key hierarchy. Online clinic payments settle directly to that clinic's merchant/bank account and do not pass through the SaaS platform's bank account. Gateway credentials are never exposed to the browser, bot, affiliate or other tenants. Deposit policy supports `NO_DEPOSIT`, a clinic-wide fixed/percentage default, and a per-service override. The calculated deposit is snapshotted on the PaymentAttempt in whole IRR. Provider-specific gateway adapters must define initiation, server-side verification, idempotency, refunds, timeout ambiguity, webhook signature verification and reconciliation.
708. `DEPOSIT_DEDUCTION` is **not** a payment method: using an existing patient credit to pay an invoice is an internal allocation, not new money received. It must be represented by a credit/prepayment allocation and must not inflate cash, POS or bank collection totals.
709. Receipts and their allocations must support partial payments, multiple payments for one invoice, and one payment allocated across multiple invoice items/invoices where the business workflow permits it. Allocation history must be auditable and corrected through an explicit reversal/reallocation mechanism, not silent destructive edits.
710. Prepayments/deposits must represent actual money received in advance. They create an available patient-credit balance that can be allocated to later charges or refunded under policy. Applying a deposit reduces available credit and the relevant invoice balance but does not create a second receipt.
711. Patient credit and invoice debt are derived from the posted charge, receipt, allocation, refund and adjustment facts. A cached balance may be used for performance only if it is transactionally maintained and verifiably rebuildable from those facts; it is not an independent source of truth.
712. A refund must be a separate immutable financial record linked to the original receipt and, when applicable, to the original invoice line/service/appointment. Partial refunds are supported. The cumulative amount refunded against a receipt/allocation must not exceed the refundable amount after prior refunds and reversals.

**712.1 — Clinic and SaaS refunds are separate bounded contexts.** `ClinicPaymentRefund` belongs to the Tenant Application Plane and is governed by clauses 712–714; it may trigger auditable revenue-share reversals under clause 720. `SaasSubscriptionRefund` belongs to the SaaS Control Plane and reverses SaaS subscription/affiliate amounts only. The two refund types must not share ledgers or database tables.
713. A refund records the actual refund method, timestamp, operator, reason, shift/context and destination/instrument reference when applicable. The refund method need not be identical to the original payment method, but that difference must be explicit and reportable.
714. Cancelling an appointment does not itself prove that money was refunded. A refund records money returned; a no-payment cancellation or a reduction of an unpaid charge must use the appropriate cancellation/financial-adjustment path instead. Original receipts and invoices must remain historically explainable.
715. Revenue sharing must support the operational categories `CLINIC`, `DOCTOR`, `SPECIALIST` (therapist/کارشناس as defined by clinic terminology) and `REFERRER`. The data model must not assume that an invoice line can have only one provider or one beneficiary if the business rules permit multiple beneficiaries.

**715.1 — `REFERRER` means only `ClinicServiceReferrer`.** The Section 50 `REFERRER` beneficiary is a person or partner who referred a patient/service to this clinic and whose revenue share is recorded inside that tenant. It is not a SaaS affiliate. `SaasAffiliatePartner` refers clinics to purchase the SaaS subscription and is a separate Control Plane domain with separate tables, permissions and ledger. No clinic names, patient records or staff data may be exposed to SaaS affiliates.
716. Revenue-share allocations should be represented as child allocation records linked to the relevant invoice/service line, with beneficiary type/ID, calculation basis, rule/rate or fixed-amount snapshot, amount in integer IRR, and applicable rule version. Reports may expose convenient totals such as clinic share, doctor share, specialist share and referrer share without storing contradictory duplicate totals as independent truth.
717. The revenue-share policy must define the distributable base, percentage/fixed rules, rounding method, precedence and eligibility rules. The sum of shares must satisfy that policy's explicit upper bound; the application must not assume without evidence that every share is calculated from gross tariff or that all share categories are always additive in the same way.
718. Revenue-share rules and calculated amounts are snapshotted for historical reporting. Later changes to rates, staff assignments, referrer rules or catalog prices must not recalculate past work.
719. Revenue-share reporting is in scope; payroll and actual payment of salaries/commissions to staff are not in scope unless separately approved. A reported earned share must not automatically be represented as having been paid to its beneficiary.
720. When a posted service/invoice line is refunded, cancelled after posting or financially reduced, the original revenue-share snapshot remains intact. Any necessary reversal/reduction of reported shares must be represented as a linked, auditable share-adjustment/reversal so gross and net performance remain distinguishable.
721. Every receipt, refund, deposit receipt, financial adjustment and share adjustment must record `occurred_at`, `operator_user_id`, actor type/identity, correlation/audit context and applicable `department_id`. `shift_id` is recorded whenever the transaction occurs within a defined cashier shift/session; historical operator identity must not be overwritten when a user changes name or is deactivated.
722. A minimal `CashierShift`/cashier-session concept must support the shift filters required by clinic operations. Where the clinic performs shift closing, it should record opening/closing users and times, opening cash float, system-calculated expected cash, counted cash and variance. POS totals must be reconciled by terminal separately from physical cash. If formal shift closing is not enabled, the transaction still records its user and configured shift label/context.
723. Cashier reports must be based on actual receipt/refund transaction time and instrument, not merely on invoice date or service-performance date. Reports must separately label billed/performed amounts, expected insurance amounts, actual cash collected, refunds, net collections, patient debt and unapplied patient credit.
724. The required manager/reporting surface must include, at minimum:
   - Doctor and specialist performance by service, including service count, gross performance, discounts/subsidy/rounding, basic and supplementary insurance shares, patient responsibility, clinic share and beneficiary shares.
   - Referrer performance/revenue-share report.
   - Free/insured/self-paying patient and service-volume statistics, including daily and monthly summaries/charts.
   - Collections and cash flow by operator, patient, date/time, shift, payment method and POS terminal, including refunds and net collections.
   - Daily prepayments/deposits, available patient credit and patient-debtor reports.
   - Visit returns, cancellations with financial effect, refunds and related original invoice/receipt references.
   - Insurance list preview/print/export, with the insurance fields and totals required by the verified clinic workflow.
   - The manager-facing ad-hoc appointment scheduling report («گزارش وقت‌دهی موردی») observed in the legacy report menu. This is an Appointment-domain/read-report requirement, not a financial ledger operation; inventory its actual columns, filters and date semantics from the legacy UI/data before implementing it.
725. Reports must support, where meaningful, filters by admission/registration date and time, service date and time, invoice/posting date and time, receipt/refund date and time, invoice number, receipt number, patient dossier/file number, patient, operator, shift, doctor, specialist, referrer, specialty, department, service, basic insurer, supplementary insurer, patient occupation, payment method and POS terminal. Admission/registration time is a distinct business timestamp and must not be inferred from the appointment start, service-performance timestamp, invoice-posting timestamp or receipt/refund timestamp. Every date/time filter must state which business timestamp it uses.
726. Patient, visit/admission and financial metadata needed for reporting must be linked through stable IDs. Where the clinic records admission/registration/check-in, persist its actual timestamp on the relevant visit/admission record and link that record to the relevant appointment, service record and financial documents as appropriate; do not fabricate it when the legacy source did not capture it. Mutable attributes such as patient occupation, provider assignment and insurance policy must be snapshotted on the relevant posted charge/service when historical reports require the value as it was at that time; do not duplicate every mutable patient field on every financial row without a reporting need.
727. Insurance preview/export is an operational reporting capability, not an assumption that the system integrates with every insurer or submits claims automatically. Any future insurer API/claim workflow must be a separate integration with its own mapping, status lifecycle and idempotency contract.
728. Read/report queries may use well-indexed SQL views or dedicated read models where measurements justify them. A separate CQRS/event-sourced reporting architecture is not mandatory solely to generate these reports. Reports must not mutate financial source records.
729. Exports and printouts containing patient, insurance or financial details must be permission-protected, audited when appropriate, limited to necessary data and generated only for authorized roles. Excel export is a manager capability unless an explicit permission grants it to another role.
730. Required indexes and query plans must be chosen from actual reporting filters and expected clinic volume. Do not create an index for every field automatically; prove that critical manager/cashier reports remain responsive on representative data.
731. Legacy migration must map the old software's labels and formulas—including «عملکرد مرکز»، «سهم کارشناس»، «سهم معرف»، «آزاد/بیمه»، «رایگان»، «رند شده»، cash/POS collection and refund reports—to explicit new fields and derived reports. If a legacy label has ambiguous semantics, inventory and verify it against actual old records before migration; do not silently guess or discard it.
732. Financial migration validation must reconcile representative historical totals by date, service, provider, operator, payment instrument and insurance category; verify receipt/refund references; and report any legacy inconsistencies for review rather than silently adjusting them.
733. Automated tests must cover at least: full and partial payment; multiple payments per invoice; unapplied prepayment and later allocation; debt calculation; refund limits and partial refunds; discount/subsidy/rounding arithmetic; insurer expected share versus actual settlement; multiple POS terminals; shift/operator filtering; admission/registration date-time filtering independently from service, invoice-posting and receipt/refund timestamps; share calculations and rule snapshots; share reversals after refunds; human-number uniqueness under concurrency; permissions for discounts and exports; and accuracy of the required reports against known fixture totals.
734. The Definition of Done for any financial feature includes a tested reconciliation identity, immutable posted history, correct audit/operator attribution, authorized access, idempotent behavior for retryable writes, and reports that distinguish billed amount from money actually received.
735. No report or user-interface label may imply tax/legal compliance, actual insurer payment, actual staff payout or cash receipt unless the underlying state supports that claim.
736. This section clarifies and expands the financial domain without reopening the frozen core architecture. Implementation must follow it; any genuinely incompatible legacy behavior must be recorded as a migration decision or narrowly scoped Architecture Change Record rather than silently changing the financial model.
737. Based on the legacy report examples described during review, the label «عملکرد مرکز» appears to correspond to `net_chargeable_amount`, while `gross_service_amount` may be reconstructible as «عملکرد مرکز + رایگان/تخفیف» for those examples. Treat this as a provisional legacy-mapping hypothesis, not a universal formula, until it reconciles against representative source rows, invoice/service details and insurance/payment breakdowns. Do not hard-code the mapping solely from a label or two sample rows.
738. The legacy column label «نقدی» must not automatically be mapped to actual cash received or `payment_method = CASH`. First establish whether it denotes patient responsibility/self-pay (as opposed to insurer responsibility) or the actual payment instrument. Keep `patient_payable_amount` / patient responsibility distinct from actual `PaymentReceipt` records and payment methods. Actual cash collection reports must be derived from posted receipts whose payment method is `CASH`, net of relevant refunds, not from a billing/report category named «نقدی».
739. The ad-hoc appointment report in clause 724 must be implemented from the Appointment-domain reporting/read model using the columns, filters, status meanings and date basis verified from the legacy application. It must not be fabricated from financial rows or mutate appointments while reporting. Add representative fixture-based tests once the legacy report semantics are inventoried.

# 51. Multi-Tenancy, Tenant Referential Integrity and Row-Level Security

740. The ecosystem consists of two strictly bounded planes deployed across three logical PostgreSQL database boundaries: (a) the SaaS Control Plane database, which manages SaaS customer accounts, tenant lifecycle, subscriptions, SaaS billing/refunds, coupons, affiliate accounts/ledger, entitlement/license issuance, contract acceptance, deletion tombstones and platform operations; (b) the shared Cloud Tenant Application database, which manages Cloud tenant clinic operations and online reservations, with every row scoped to one immutable UUIDv7 `tenant_id`; and (c) each clinic's Local Hub PostgreSQL database on its Mini PC, which is authoritative for physical reception and other explicitly local operational activity while disconnected. The Control Plane database and Cloud Tenant Application database have separate credentials, migration lineages and API trust boundaries. A Local Hub uses the tenant-domain schema/migration baseline with explicitly documented local-only metadata. These are logical database boundaries even if Cloud databases share a physical managed PostgreSQL cluster. No cross-database foreign keys are permitted; cross-boundary references use immutable IDs and versioned APIs/integration events.

741. Every tenant-owned table other than the root `tenant_registry` must have `tenant_id UUID NOT NULL REFERENCES tenant_registry(tenant_id)`. This direct root foreign key is required on every tenant-owned root/aggregate table (including `tenant_persons`, `services`, `bookable_resources`, `appointments`, `patient_profiles` and inventory roots), and may also be present on child tables for explicit tenant existence integrity. No tenant-owned row may be created for a nonexistent tenant, with a null tenant_id or with a client-forged tenant context. The `tenant_registry.tenant_id` itself is the root primary key and is not a self-referencing foreign key.

742. Every tenant-owned parent table referenced by a composite foreign key must expose `UNIQUE (tenant_id, id)` in addition to its primary key. This applies to appointments, resources, persons, services, invoices, receipts, inventory entities and other tenant-owned aggregates where referenced.

743. Every foreign key between tenant-owned tables must include `tenant_id`, referencing `(tenant_id, id)` on the target table. For mandatory relationships, both referencing columns must be `NOT NULL`; `MATCH FULL` is permitted and recommended where all referencing columns are mandatory. For an optional composite relationship such as `(tenant_id, specific_resource_id)` or `(tenant_id, booker_person_id)`, where `tenant_id` is `NOT NULL` and the target ID is `NULLABLE`, the foreign key must use `MATCH SIMPLE` (or omit the match clause, because PostgreSQL defaults to `MATCH SIMPLE`); it must not use `MATCH FULL`, since `MATCH FULL` rejects a partially NULL composite key. The separate direct `tenant_id REFERENCES tenant_registry(tenant_id)` constraint still verifies tenant existence when the optional target ID is NULL. A plain ID-only foreign key is insufficient for tenant-owned relationships.

744. Database roles are separated per plane and PostgreSQL cluster. For the Tenant Application Plane, `db_migrator` is a non-login migration/ownership role that owns only Tenant Plane schemas/tables and executes Tenant Plane Alembic migrations; `db_app_runtime` is the non-owner application/worker role and is not a `SUPERUSER`, does not have `BYPASSRLS`, is not granted `TRUNCATE`, DDL, ownership or policy-management privileges, and is never a member of `db_migrator`. Because PostgreSQL role names are cluster-wide, when the Cloud Control Plane DB and Cloud Tenant Application DB share a cluster, the Control Plane uses distinct non-login group roles `cp_db_migrator` and `cp_db_app_runtime` with the same respective migration/ownership and least-privilege runtime purposes, scoped only to Control Plane objects. Each plane has separate narrowly scoped migration and runtime login principals; a runtime login inherits only its own plane's runtime role and is never a direct or transitive member of any migrator role or the other plane's runtime role. The migration login may assume only its corresponding plane-specific migrator role and only in controlled CI/deployment migration jobs. Each independent Local Hub PostgreSQL instance has its own cluster-wide role namespace and may reuse the Tenant Plane group-role names. Migration credentials and secrets must not exist in Local Hub, Cloud Hub, Control Plane or worker runtime containers/images/environment. Backup/restore operators use a separately controlled identity and are not ordinary query users.

745. RLS is mandatory on every tenant-owned table in a shared multi-tenant database. The Cloud Hub shared tenant database must enable and force RLS on every such table. A Local Hub deployment containing only one tenant may use the same policy pattern for consistency; if a Local Hub database ever contains more than one tenant, RLS is mandatory there as well.

746. Each RLS-protected tenant table uses a permissive base policy together with a restrictive tenant guard for runtime access. Because `FORCE ROW LEVEL SECURITY` also subjects the table owner to RLS, a separate migration-only permissive policy must be created for `db_migrator`. The migration policy is not inherited by or available to runtime roles. The base runtime policy grants no authority beyond SQL table grants; the restrictive runtime policy remains an AND guard even if feature-specific permissive policies are added later:

```sql
ALTER TABLE appointments ENABLE ROW LEVEL SECURITY;
ALTER TABLE appointments FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_runtime_base ON appointments
AS PERMISSIVE
FOR ALL TO db_app_runtime
USING (true)
WITH CHECK (true);

CREATE POLICY tenant_isolation_guard ON appointments
AS RESTRICTIVE
FOR ALL TO db_app_runtime
USING (
  tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
)
WITH CHECK (
  tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
);

-- FORCE ROW LEVEL SECURITY applies to the table owner as well.
-- This permissive policy is for the migration role only.
CREATE POLICY tenant_migrator_maintenance ON appointments
AS PERMISSIVE
FOR ALL TO db_migrator
USING (true)
WITH CHECK (true);
```

The `tenant_migrator_maintenance` policy does not grant SQL privileges by itself; ordinary PostgreSQL grants still apply. The migration role is used only by authorized migration jobs. `db_app_runtime` and every runtime login/worker role must not be a member of `db_migrator`, and runtime containers must not contain migration credentials. Apply the three-policy pattern consistently to each table where the named roles apply; do not create a migrator policy for an unrelated role or expose it through role inheritance.

747. At the start of every Tenant Application Plane UoW, including HTTP requests and background jobs, the tenant context is bound only within that database transaction using `SELECT set_config('app.current_tenant_id', :verified_tenant_id, true)`. The transaction-local setting must not leak through the connection pool.

748. `verified_tenant_id` must derive from server-verified credentials or a signed internal job envelope: verified JWT claim, verified Ed25519 node identity, or authorized internal command context. A tenant identifier supplied only in request JSON/query/path is never the authority for database context.

749. RLS is defense in depth, not a substitute for safe SQL or repository scoping. SQL must use bound parameters; dynamic identifiers/clauses must use allowlists; repositories must explicitly scope reads and writes by tenant. A SQL injection in a session able to call `set_config` may alter a custom GUC, so parameterization and least privilege remain mandatory.

750. Views, partitioned tables, row-level triggers and functions that access tenant data must be included in the Threat Model. On PostgreSQL 15+, tenant-facing views should use `security_invoker = true` where compatible. `SECURITY DEFINER` functions for general tenant queries are prohibited unless an ACR documents why they are necessary and how they enforce tenant scope internally. `TRUNCATE` is not protected by RLS and is not granted to runtime roles.

751. Testcontainers security tests run with the actual `db_app_runtime` role and cover cross-tenant `SELECT`, `INSERT`, `UPDATE`, `DELETE`, foreign-key attachment, views and worker execution. Tests must also prove that missing tenant context fails closed and that RLS is not bypassed through owner/superuser credentials.

752. Multi-Branch / Parent Organization hierarchy is out of scope. Each clinic tenant is an independent SaaS tenant; cross-tenant consolidated reporting is not exposed to clinic tenants.

753. The SaaS Marketing & Storefront is a separate project/surface and interacts with the Control Plane only through approved onboarding, pricing, coupon, checkout and subscription APIs. It has no direct access to Tenant Application Plane tables.

754. Each clinic's Public Website and Patient Portal (`MOD_WEB_PANEL` or the separately entitled clinic website module) consume approved Cloud Hub APIs scoped to that clinic tenant. They never connect directly to Local Hub PostgreSQL and cannot bypass Business API policies.

# 52. Person Identity, Optional Official Identifiers and Cryptographic Data Lifecycle

755. Providing a National ID or foreign official identifier is optional across the platform. No patient, staff member, clinic owner/manager, receptionist, doctor, specialist or SaaS customer may be blocked from account/profile creation solely because an official identifier is absent, except where a separately verified legal requirement for a particular transaction is documented and counsel-approved.

756. `SaasCustomerAccount` is a Control Plane identity authenticated by a verified mobile number/OTP. Its identity is independent of `tenant_persons`; there are no cross-plane foreign keys. If a formal SaaS invoice requires buyer legal identifiers, they belong in an isolated Control Plane billing-profile table and are collected only when necessary.

757. The Tenant Application Plane uses `tenant_persons` as the canonical human identity record. Its core columns include UUIDv7 `id`, `tenant_id`, name fields, optional birth date/gender where required, aggregate version and timestamps. Personal identity must not be inferred from an appointment, phone number or mutable display name.

758. `person_identifiers` stores zero or more optional official identifiers for a person. Absence of an official identifier means zero rows, not a dummy value or a NULL placeholder row. Identifier uniqueness is tenant-scoped and type/issuing-authority-scoped.

759. `person_phones` stores zero or more contact phone records for a person. Multiple persons in one tenant may share the same phone number (for example family members); phone number is not a unique person key and `is_shared_phone` is informational only.

760. `patient_profiles` has a zero-or-one relationship to `tenant_persons` per tenant and contains the operational dossier, staff-only tags, internal notes and pinned reception alerts. It is not a full EMR, prescription or clinical decision-support record.

761. `staff_profiles` has a zero-or-one relationship to `tenant_persons` per tenant and stores staff/provider metadata. `medical_council_code` is a separate optional professional identifier and is not a National ID.

762. `user_accounts` has a zero-or-one relationship to `tenant_persons` per tenant and stores access credentials and account state. Doctors/specialists do not receive a login by default in the initial scope; a user account exists only when the person is expressly authorized to use the panel. The staff-management form must expose a permission-protected opt-in control labelled `Create login account` for every staff/provider type, including doctors and specialists. It is OFF by default. When explicitly enabled by an authorized manager, the workflow creates the person's `user_accounts` row, provisions an account-specific tenant-unique login identifier and securely establishes credentials. Staff kind or provider status must never grant permissions automatically; RBAC assignments are separate and explicit. Disabling/removing login access must not delete the staff profile or historical audit identity. Shared family phone numbers must not be silently reused as a unique login identifier.

763. `tenant_governance_assignments` links roles such as `CLINIC_OWNER`, `LEGAL_REPRESENTATIVE` and `CLINIC_MANAGER` to `tenant_persons` through composite `(tenant_id, person_id)` foreign keys. Governance, patient and staff records must not duplicate a person's National ID in multiple tables.

764. Tenant-level legal entity fields (for example legal entity type, company registration/national identifier, permit number and medical-center code) are separate from a natural person's National ID. They are nullable/optional unless a verified legal requirement for a specific service or invoice is documented. A company's legal identifier must never be confused with an individual's 10-digit National ID.

765. Identifier normalization is type-specific and applies only to identifier fields, never free text. Persian and Arabic digits are mapped to ASCII digits; approved visual separators/whitespace are normalized; leading zeros are preserved. Each identifier type has its own allowed character set, length and validation rule. Iranian National ID Modulo-11 validation establishes only syntactic validity, not identity ownership. Foreign FIDA-code rules must be confirmed against the applicable authoritative requirements; passport validation must be issuer/country-aware rather than assuming one universal format. Manual document review is not labelled official verification.

766. `person_identifiers` stores encrypted value, 96-bit GCM nonce, 128-bit authentication tag, encryption key version, AAD version, masked display, identifier type, issuing authority and verification status. A separate blind index supports exact lookup without storing the raw identifier in plaintext.

767. The domain-separated HMAC blind-index input is:

```text
canonical_id_input =
    LOWER(TRIM(tenant_id_uuid_string))
    + "|" + UPPER(TRIM(id_type))
    + "|" + UPPER(TRIM(issuing_country_or_authority))
    + "|" + NORMALIZED_IDENTIFIER_VALUE

lookup_hmac = HMAC_SHA256(
    key = secret_hmac_key(hmac_key_version),
    message = UTF8_ENCODE(canonical_id_input)
)
```

The active blind-index uniqueness scope is `(tenant_id, id_type, issuing_country_or_authority, lookup_hmac_active)`. HMAC keys are stored in managed secret/key infrastructure, never in the database or source control.

768. Phone numbers are PII and must not be stored only as plaintext. `person_phones` stores an AES-256-GCM ciphertext of the normalized E.164 value, nonce/tag/key version/AAD version, masked value, `phone_lookup_hmac`, `is_primary`, `is_shared_phone` and `phone_verified_at_utc`. The lookup index `(tenant_id, phone_lookup_hmac)` is non-unique to support shared family phones. Phone verification is distinct from phone entry.

769. AES key rotation and HMAC key rotation are independent lifecycles. AES rotation decrypts and re-encrypts source values using a new encryption key and new unique nonce; HMAC rotation recomputes the blind index from decrypted/canonicalized source values. Neither operation substitutes for the other.

770. AES-256-GCM encryption must use a cryptographically random unique 96-bit nonce per key, a 128-bit authentication tag and a versioned AAD contract. AAD v1 binds at least tenant, person, record, data-field/identifier type and issuing authority. Example:

```text
aad_bytes_v1 = UTF8_BYTES(
  "v1|" + LOWER(tenant_id)
  + "|" + LOWER(person_id)
  + "|" + LOWER(record_id)
  + "|" + UPPER(id_type_or_field_type)
  + "|" + UPPER(issuing_country_or_authority)
)
```

Nonce reuse with the same AES-GCM key is prohibited. AAD version and encryption key version must be stored alongside ciphertext. AAD prevents ciphertext transplant across tenants/persons/records when the decryptor reconstructs and verifies the same context.

771. HMAC rotation follows a controlled expand/backfill/cutover/contract procedure: (1) add the next-version blind-index storage and metadata; (2) deploy code that dual-writes old and new indexes while the old unique index remains authoritative; (3) verify every old application/worker instance has been drained; (4) run an idempotent batched backfill; (5) verify no missing new hashes and no duplicate collisions; (6) build the new unique index with `CREATE UNIQUE INDEX CONCURRENTLY` in a dedicated Alembic non-transactional/autocommit migration; (7) inspect `pg_index.indisvalid`, drop and retry an invalid index after resolving its cause; (8) validate non-null/check constraints and switch active read/uniqueness key metadata while retaining a defined rollback window; (9) after rollback assurance, remove old index/column and retire the old key. No `Zero-Race-Window` claim is made without successful multi-version concurrency testing.

772. During HMAC dual-write, old and new indexes must be calculated from the same canonical source value in the same write transaction. Existing old application versions that write only the old index must be fully drained before new-index completeness is asserted. New writes must never bypass the current active uniqueness rule. Partial/failed concurrent index creation must be detected and remediated before cutover.

773. Patient merge continues to use the v1.3 canonical/alias model. Merge must be authorized, idempotent where retried, append-audited, and preserve appointments, invoices, receipts, refunds and historical identity references. A blind-index collision or duplicate identifier must not trigger automatic patient merge.

774. Verification state is explicit: `SYNTACTICALLY_VALID_UNVERIFIED` means only format/check-digit validation passed; `OFFICIALLY_VERIFIED` requires a trusted official verification source and timestamp. Any document reviewed manually must use a separate accurately named state.

775. Identifier and phone lookup APIs must not expose raw blind indexes, ciphertext, nonce, authentication tags or key-version secrets. Masked displays are least-privilege outputs; access to decryptable values is separately permissioned and audited.

# 53. Dual-Pool Scheduling, Multi-Resource Allocation and Hold Lifecycle

776. Each row in `bookable_resources` represents one atomic capacity unit (`capacity = 1`) for online exclusion. Clinics with multiple beds/rooms/devices or parallel default online streams create one resource row per independently bookable unit. A generic default stream is not a single global unit unless the clinic intentionally wants only one concurrent online appointment.

777. Each service defines resource requirements in `service_resource_requirements`, with tenant-scoped composite foreign keys to `services` and any `specific_resource_id`. Each requirement has a `requirement_group`, required resource type, optional specific resource, and positive `quantity_required`. All mandatory groups must be satisfied. Alternative resource types/identities within a group must have explicit OR semantics; separate groups are conjunctive. The handler must validate that every required atomic unit is allocated. A migration must prevent a requirement from pointing to another tenant's service/resource.

778. `booking_channel` is immutable event/business context: `ONLINE_WEB`, `ONLINE_BOT` or `MANUAL_STAFF`. `capacity_pool` is deterministically derived: both online channels map to `ONLINE`; `MANUAL_STAFF` maps to `MANUAL`. The database CHECK constraint rejects invalid mappings.

779. Authorized manual bookings may overlap ONLINE and other MANUAL allocations by explicit business decision. Before commit, the API/UI must return the exact conflicting appointments (IDs, display-safe patient names, channels and time intervals); the staff member must set `acknowledge_overlap = true` and hold `ALLOW_MANUAL_OVERBOOKING`. The transaction writes an immutable audit entry containing operator, timestamp, new appointment ID and the conflict IDs/snapshot. If the conflict list changes before commit, the handler must re-check within the transaction and require confirmation of the current list. This rule is not a capacity override for ONLINE bookings.

780. `appointment_resource_allocations` stores one allocation per required atomic resource with `tenant_id`, `appointment_id`, `resource_id`, `booking_channel`, `capacity_pool`, `allocation_status` and bounded `time_slot TSTZRANGE`. Parent tables must expose composite unique `(tenant_id, id)` keys. The following invariant template applies (names may be adapted in migration, but semantics may not):

780.1. `appointments` includes an optional `patient_booking_note TEXT NULL` for a short note supplied by the beneficiary/booker during booking, or transcribed by an authorized receptionist on the person's request. This is not an internal staff note, diagnosis, EMR entry or clinical decision record. It must be length-limited at the API/database boundary, visible only to the associated beneficiary/booker under the applicable portal/consent rules and authorized clinic staff, and excluded from public website content, unrelated patient views and general bot payloads. Internal staff annotations remain in their separately permission-protected staff-only note domain and must never be placed in `patient_booking_note`. The actor who supplied or transcribed the note is auditable.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE appointments
  ADD CONSTRAINT uq_appointments_tenant_id UNIQUE (tenant_id, id);

ALTER TABLE bookable_resources
  ADD CONSTRAINT uq_bookable_resources_tenant_id UNIQUE (tenant_id, id);

CREATE TABLE appointment_resource_allocations (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  appointment_id UUID NOT NULL,
  resource_id UUID NOT NULL,
  booking_channel VARCHAR(32) NOT NULL,
  capacity_pool VARCHAR(16) NOT NULL,
  allocation_status VARCHAR(32) NOT NULL,
  time_slot TSTZRANGE NOT NULL,
  CONSTRAINT fk_alloc_appointment_tenant
    FOREIGN KEY (tenant_id, appointment_id)
    REFERENCES appointments (tenant_id, id),
  CONSTRAINT fk_alloc_resource_tenant
    FOREIGN KEY (tenant_id, resource_id)
    REFERENCES bookable_resources (tenant_id, id),
  CONSTRAINT ck_alloc_valid_bounded_time_slot CHECK (
    NOT isempty(time_slot)
    AND NOT lower_inf(time_slot)
    AND NOT upper_inf(time_slot)
    AND lower_inc(time_slot)
    AND NOT upper_inc(time_slot)
    AND lower(time_slot) < upper(time_slot)
  ),
  CONSTRAINT ck_alloc_channel_pool_match CHECK (
    (booking_channel IN ('ONLINE_WEB', 'ONLINE_BOT') AND capacity_pool = 'ONLINE')
    OR (booking_channel = 'MANUAL_STAFF' AND capacity_pool = 'MANUAL')
  ),
  CONSTRAINT uq_appointment_resource_allocation
    UNIQUE (tenant_id, appointment_id, resource_id),
  CONSTRAINT no_overlapping_online_resource_allocations
    EXCLUDE USING gist (
      tenant_id WITH =,
      resource_id WITH =,
      time_slot WITH &&
    ) WHERE (
      capacity_pool = 'ONLINE'
      AND allocation_status IN ('PENDING_PAYMENT_HOLD', 'CONFIRMED', 'CHECKED_IN')
    )
);
```

The migration must verify `btree_gist` support in the target PostgreSQL deployment. The SQL above is a contract template and must be adapted to the final table definitions, indexes and migration ordering without weakening the invariants.

781. The appointment and allocation states are changed in the same UoW/DB transaction. Canonical mapping is: `PENDING_PAYMENT_HOLD`→`PENDING_PAYMENT_HOLD`; `CONFIRMED`→`CONFIRMED`; `CHECKED_IN`→`CHECKED_IN`; `COMPLETED`→`COMPLETED`; `CANCELLED`→`CANCELLED`; `EXPIRED_HOLD`→`EXPIRED_HOLD`; `NO_SHOW`→`NO_SHOW`. The EXCLUDE predicate includes only `PENDING_PAYMENT_HOLD`, `CONFIRMED` and `CHECKED_IN`. `COMPLETED`, `CANCELLED`, `EXPIRED_HOLD` and `NO_SHOW` do not occupy active online capacity. `NO_SHOW` releases remaining capacity only when its transition is valid under the scheduled-time/state policy; it must not be applied prematurely.

782. Hold expiry uses both a background `HoldExpirationWorker` and inline lazy eviction. The worker must not claim due work by locking an Appointment row with `FOR UPDATE SKIP LOCKED`, because that would violate the global Resource → Appointment → Allocation lock order in clause 783. Instead, it claims a due `hold_expiry_work_items` row (or performs an unlocked candidate-ID scan) in a short, separate claim transaction, records a lease/claim token, and commits. In a new scheduling UoW it resolves the complete resource set, then follows the exact global lock order in clause 783. Before mutation it revalidates the claim token, current `hold_expires_at_utc <= database_utc_now`, `appointments.status = 'PENDING_PAYMENT_HOLD'`, and the current resource/allocation set. It then changes the Appointment and all Allocation statuses atomically or marks the work item no-op/retryable. Inline lazy eviction uses the same UoW, same resource-first lock order and same revalidation rules before a conflicting ONLINE allocation is inserted; it only expires holds whose expiry is due and whose current resource/time ranges actually conflict. Queue claiming is not the business-state lock and never substitutes for the final EXCLUDE constraint.

783. All operations that inspect or mutate allocation business state (HoldExpirationWorker, ScheduleAppointmentHandler, VerifyPaymentHandler, cancellation/reschedule handlers and manual-overlap acknowledgement) use one global lock order: first lock all involved `BookableResource` rows ordered by `resource.id ASC`; next lock all involved parent Appointment rows ordered by `appointment.id ASC`; finally lock Allocation rows ordered by `(appointment_id ASC, resource_id ASC, allocation_id ASC)`. The worker's separate `hold_expiry_work_items` lease/claim row is claimed before the business UoW and is not an Appointment/Resource/Allocation lock; no Appointment row may be locked during the claim phase. A handler that does not yet have an appointment ID must resolve the resource IDs without taking parent/child business locks first. If the resource set changes between discovery and lock acquisition, the handler must safely restart/re-resolve before mutating. All booking writers, including ONLINE and MANUAL, follow this order. After acquiring locks, the handler rechecks the current state, expiry, resource set and allocation set. Locking resource rows serializes the conflict snapshot for MANUAL acknowledgement; MANUAL remains allowed to overbook. `SKIP LOCKED` is used only for the work-queue claim selection; the final `EXCLUDE` violation (`23P01`) remains the authoritative concurrent ONLINE conflict. Deadlock-freedom is not claimed solely from sorted UUIDs; it must be verified with concurrency tests and database deadlock monitoring.

784. Payment verification records `provider_paid_at_utc` only when returned by a trusted provider Verify API and separately records `callback_received_at_utc`. Client-submitted timestamps are never authoritative. If the provider does not supply a trustworthy payment timestamp, the system does not infer that payment occurred before the hold expired.

785. For a verified payment callback after `EXPIRED_HOLD`: if trusted `provider_paid_at_utc` is at or before the original hold expiry and the required slot is still free, the handler may atomically reacquire all allocations and confirm, subject to the EXCLUDE constraint. If any competing ONLINE booking owns any required resource, it is never cancelled or overwritten; the verified receipt becomes an unapplied prepayment or an explicitly unreconciled verified receipt if payer mapping is ambiguous, and the patient is offered an alternative slot or refund. If payment actually occurred after expiry, or its actual time cannot be verified, the appointment is not auto-confirmed; the verified money is reconciled separately and may become credit/refund under policy.

786. A failed/ambiguous payment verification must not create a `PaymentReceipt` or `UnappliedPrepayment`. Provider amount, merchant ID, order/payment attempt ID, currency, settlement status and unique reference must match the immutable PaymentAttempt. Duplicate provider callbacks are idempotent.

787. MANUAL allocations do not enter the ONLINE EXCLUDE predicate and therefore may overlap. This is intentional. After sync, the Cloud read model records both the MANUAL appointment and any collision indicator. Sync must not modify `booking_channel`, `capacity_pool` or source authority.

788. All appointment time values are stored as UTC instants and ranges are half-open `[start_utc, end_utc)`. Presentation uses the clinic's configured time zone/Jalali calendar. Time-slot creation rejects empty, unbounded or non-positive ranges. Two appointments whose adjacent ranges share an endpoint do not overlap.

789. The online booking API returns a safe capacity conflict when the final PostgreSQL exclusion constraint rejects a competing allocation. MANUAL collision acknowledgement is a separate workflow and must never be converted into an online capacity-conflict bypass.

790. Required scheduling tests include same-resource concurrent ONLINE reservations from website and bot; multi-resource atomic failure; missing service requirement; adjacent ranges; expired hold worker vs. inline booking; payment callback vs. hold expiry; late verified payment with free/taken slot; concurrent manual overbooking acknowledgement; tenant cross-link attempts; sync of MANUAL channel; and status/allocation synchronization.

791. `ACR-v3-002` is the accepted product/architecture decision for the dual pool, subject to closing the tests and open items. No implementation may reintroduce a single `room_id` as the sole allocation model.

# 55. SaaS Onboarding, Demo Conversion and Contract Acceptance

796. A new customer may purchase directly or start a 14-day trial (`TRIAL_ACTIVE`). Trial expiry enters a clearly defined 7-day retention/conversion window (`TRIAL_EXPIRED_RETENTION`). At paid conversion, the buyer makes one explicit, one-time and irreversible choice: (a) convert and keep Demo data/configuration; or (b) convert and start with a clean operational environment. The paid subscription becomes `ACTIVE` only after the required payment is verified and conversion operations complete successfully.

797. Under clean conversion, all Demo operational records, files, settings and caches within the tenant operational scope are purged without a hidden Safety Snapshot; any registered Demo Local Hub node is revoked and its local database must be reinitialized before pairing with the clean tenant. Only explicitly identified Control Plane commercial records needed to evidence the purchased subscription remain. The buyer must see exactly what will be removed before confirming. The choice cannot be repeated after activation.

798. If no purchase is completed within seven days after trial expiration, the tenant enters the deletion pipeline. Cloud deletion and Local Hub wipe are tracked separately; an offline node must not be reported as wiped. There is no `Factory Reset`, `Tenant Reset`, `Platform Reset`, equivalent button, endpoint, command or hidden workflow after paid activation in the Clinic Owner panel, Manager panel or Super Admin Portal. The only clean-start choice is the one-time Demo-to-paid conversion choice.

799. Before trial activation/checkout, the SaaS customer reviews the versioned agreement, checks an explicit acceptance box and verifies a purpose-bound OTP such as `CONTRACT_ACCEPTANCE_OTP`. An immutable `ContractAcceptanceRecord` stores contract version and SHA-256 content hash, accepted timestamp UTC, SaaS account ID, tenant ID where applicable, verified-phone reference/hash, OTP challenge ID, acceptance session ID and actor; IP may be stored only if legally justified. The accepted contract version must be retrievable. This is an evidentiary electronic acceptance record, not a claim of statutory PKI/certified secure electronic signature or blanket waiver of liabilities. Raw OTP is never stored in logs.

# 56. Honest Data Deletion, Tombstone Restore Guard and Full-Platform Backup

800. Each tenant has a dedicated `TenantDEK` (wrapped by the platform key-management hierarchy) for application-level sensitive fields specifically designated for encryption, including official identifiers, phone values, clinic gateway secrets and tenant-encrypted objects. Relational columns needed for business constraints/indexing (for example UUIDs, timestamps and whole-Rial amounts) may remain plaintext unless separately designed otherwise. Destroying the TenantDEK makes only the fields actually encrypted under it undecryptable; it does not erase plaintext relational values from WAL or DR backups.

801. Active Cloud deletion must purge tenant rows across all tenant-owned tables, Outbox/Inbox, read models, cache/session entries, search indexes, active Object Storage items and every historical object version/delete marker/incomplete multipart upload where the provider supports such deletion. The system records provider-level completion evidence. If a provider cannot purge a particular copy immediately, the remaining copy is disclosed with its retention deadline rather than represented as erased.

802. `TenantErasureTombstoneRegistry` is append-only and stored/replicated independently from the primary Cloud database and from the backups whose restore it guards. Each tombstone contains minimum metadata (`tenant_id`, approved deletion time, scope, version and integrity/signature material), not patient records. Its purpose and retention period are disclosed. It remains available until all pre-deletion backups/WAL/object versions capable of resurrecting the tenant have expired or been destroyed, unless counsel approves a documented longer period.

803. During any full/partial restore of a Cloud database or Object Storage, traffic remains blocked in maintenance mode until a Post-Restore Tombstone Enforcement process has loaded the latest independent tombstone registry, re-purged all deleted tenant data/keys/objects from the restored state, validated the result, and recorded a signed/audited completion report. A restore must never reopen users before this guard passes.

804. Cloud deletion state and per-node Local Hub deletion state are independent. Cloud lifecycle includes `REQUESTED`, `ACTIVE_CLOUD_DATA_PURGED`, `WAITING_FOR_BACKUP_RETENTION_EXPIRY`, and `CLOUD_ERASURE_COMPLETED`. Local node lifecycle includes `NOT_APPLICABLE_CLOUD_ONLY`, `QUARANTINED_WIPE_COMMAND_ISSUED`, `LOCAL_PURGE_ACKNOWLEDGED`, and `OFFLINE_UNCONFIRMED_LOCAL_WIPE`. The Cloud immediately revokes ordinary Sync credentials/entitlements and sends a signed `DECOMMISSION_AND_PURGE_LOCAL_DB` command when reachable. A signed `LOCAL_PURGE_ACK` is required before stating that a node has been wiped. An offline machine remains unconfirmed and may retain data on its physical disk until it reconnects or the clinic performs a documented local wipe.

805. `CLOUD_ERASURE_COMPLETED` means only that active Cloud deletion is complete and all relevant Cloud backup/WAL retention windows have expired; it does not imply an offline Local Hub was wiped. The user-facing status must separately state Cloud completion and each Local node status. No global “all data everywhere erased” claim is allowed unless each applicable node and provider confirms it.

806. Backup retention periods for base backups, WAL archives, replicas and Object Storage recovery copies must be fixed before Production and disclosed before customer acceptance. Active-record deletion does not promise immediate physical erasure from immutable backups. Backups must age out by a documented rotation policy. KMS recovery material and wrapped key metadata must be recoverable under separate custody; raw master keys must not be stored unencrypted alongside backup archives.

807. Super Admin may trigger manual/scheduled encrypted full-platform DR backups covering Control Plane database, tenant Cloud database(s), Object Storage and essential recovery metadata/configuration. Trigger and restore require MFA, role authorization, immutable audit, integrity checks and restore verification. Backup capability does not grant routine patient-record browsing. Break-glass recovery is dual-controlled, time-limited and audited; support impersonation is separate and defaults to read-only.

808. Local Hub targets from v1.3 clauses 323 and 328 remain `RPO <= 5 minutes` and `RTO <= 1 hour` only for the defined Local Hub disaster scenario. Cloud Hub, Control Plane, Object Storage and KMS have separate RPO/RTO objectives to be capacity-tested and approved before Production. A same-site NAS alone is not a failure-independent recovery copy.

# 57. SaaS Affiliate Partner Ledger, Commission Arithmetic and Anti-Abuse

809. All SaaS affiliate money is whole-Rial signed 64-bit integer money. Multiplication/intermediate arithmetic must use arbitrary-precision integer arithmetic or a sufficiently wide exact numeric type (for example `NUMERIC(38,0)`), then apply an explicitly defined rounding rule and validate the final result against `int64` bounds. Floating-point money is prohibited.

810. For a subscription invoice, `commissionable_base_irr = MAX(0, gross_plan_price_irr - campaign_coupon_discount_irr)`. The referral first-purchase discount reduces the customer's net payment but does not reduce the affiliate's commissionable base under this product policy; it is recorded separately as a platform marketing subsidy. VAT/statutory tax and SMS wallet top-ups are excluded. Campaign and referral discounts may be combined only when coupon stackability and eligibility permit; all prices/discounts/policy versions are snapshotted.

```text
customer_net_subscription_paid_irr =
    gross_plan_price_irr
    - campaign_coupon_discount_irr
    - referral_first_purchase_discount_irr

commissionable_base_irr =
    MAX(0, gross_plan_price_irr - campaign_coupon_discount_irr)

raw_commission_product =
    commissionable_base_irr * commission_rate_bps

earned_commission_irr =
    ROUND_HALF_UP(raw_commission_product / 10000)
```

For non-negative integer numerator, implementation must use exact integer arithmetic or `NUMERIC`, not binary floating point. Percentage rates are bounded by the approved platform policy. Fixed-per-month and one-time bounty policies must also be snapshotted and versioned.

811. Partial/full refund and chargeback clawback MUST use a cumulative rounding rule. Independently rounding each partial refund and summing the results is prohibited because multiple refunds can accumulate one-or-more Rial of rounding drift. For each original subscription invoice/commission source, persist (or maintain as a transactionally rebuildable projection) `original_commissionable_base_irr`, `original_commission_irr`, `cumulative_refunded_commissionable_base_irr` and `cumulative_commission_clawback_irr`. The cumulative refunded base is the net amount of verified, non-reversed refunds/chargebacks mapped to the original commissionable base and must remain within `0 <= cumulative_refunded_commissionable_base_irr <= original_commissionable_base_irr`:

```text
new_cumulative_refunded_commissionable_base_irr =
    previous_cumulative_refunded_commissionable_base_irr
    + newly_refunded_commissionable_base_irr

IF original_commissionable_base_irr == 0:
    cumulative_target_clawback_irr = 0
ELSE IF new_cumulative_refunded_commissionable_base_irr == original_commissionable_base_irr:
    cumulative_target_clawback_irr = original_commission_irr
ELSE:
    cumulative_target_clawback_irr = ROUND_HALF_UP(
        original_commission_irr
        * new_cumulative_refunded_commissionable_base_irr
        / original_commissionable_base_irr
    )

new_clawback_delta_irr =
    cumulative_target_clawback_irr
    - previous_cumulative_commission_clawback_irr
```

Post only `new_clawback_delta_irr` as the new linked ledger reversal (negative when clawing back additional commission). All calculations use exact integer/arbitrary-precision or sufficiently wide exact NUMERIC arithmetic, never floating point. The transaction locks the original affiliate commission source/account, validates idempotency, rejects a cumulative refunded base above the original base, records the refund identity and updates the rebuildable cumulative projection atomically. A reversal/correction of a previously verified refund must create a linked compensating ledger entry and recalculate the cumulative target from the net refunded base; it must never rewrite prior ledger facts. When cumulative refund reaches the original commissionable base, cumulative clawback MUST equal `original_commission_irr` exactly, regardless of the number or ordering of partial refunds. Example: original commission `+60,000,000 IRR`, prior payout `-20,000,000 IRR`, then full cumulative clawback `-60,000,000 IRR`; final wallet balance is `-20,000,000 IRR`. The clawback entry itself is the full cumulative delta needed to reach `-60,000,000 IRR`, not merely the previously withdrawn amount.

812. Affiliate ledger entries are append-only. Earnings, clawbacks and payouts are separate entries; wallet balance is derived from ledger entries (a transactionally rebuildable cache may be used). The commission lifecycle includes `PENDING_CLEARANCE` and `AVAILABLE_FOR_PAYOUT`; the payout aggregate uses `PAYOUT_REQUESTED`, `PAYOUT_PROCESSING` and `PAID`; reversal status is represented by linked `PARTIALLY_REVERSED` or `FULLY_REVERSED` entries/states without rewriting the original earning. Commissions remain in clearance until the configured refund/chargeback window expires. Concurrent payouts use idempotency and account-level locking to prevent double settlement. Any positive eligible balance may be requested without a minimum payout threshold, subject to identity/tax/bank checks approved by counsel.

813. Anti-abuse rules prohibit self-referral under the defined normalized account/phone/bank identity checks, bind at most one referrer to a tenant within a documented attribution window, and define whether renewals are commissionable. Those terms must be disclosed and snapshotted. Affiliate portals/bots show only aggregate counts/totals and anonymized referral tokens. They never show clinic names, domains/slugs, patients, staff or identifiable low-volume breakdowns that enable re-identification. Clinic service referral shares remain exclusively in Section 50.

# 58. Offline Licensing, Entitlement Propagation and Scoped Read-Only Mode

814. `LicenseLeaseToken` is signed by the SaaS Control Plane Ed25519 key and contains at least `tenant_id`, `node_id`, `lease_id`, monotonic per-node `lease_sequence`, `issued_at_utc`, `not_before_utc`, `expires_at_utc`, `grace_period_ends_at_utc`, `allowed_modules`, `feature_entitlements`, `max_lan_client_seats`, `minimum_supported_app_version` and `signing_key_id`. Emergency offline codes are bound to tenant, node, next lease sequence, challenge nonce and their own expiry and are server-signed.

815. Ed25519 prevents token forgery/tampering but does not prevent a customer with physical control from restoring an old full-disk snapshot, which can also roll back the local database, `max_observed_utc`, `license_sequence` and `challenge_nonce`. Such controls deter ordinary clock rollback and casual replay only. The absolute expiry embedded in the signed token remains authoritative. Node transfer/re-bind requires revoking the prior node and explicit signed pairing for the replacement node.

816. Cloud Hub and Bot Gateway entitlement caches have a maximum TTL of 60 seconds, with event-driven invalidation on suspension, expiration or upgrade. The design does not promise zero-millisecond global revocation. Provider/network outages must respect the bounded cache and separately defined lease/grace rules. The 60-second Cloud TTL does not shorten an already-issued offline Local Hub lease.

817. After subscription and grace-period expiry, write operations across Web, Bot and Local Hub return the defined `402 Payment Required`/license-expired business error. Read-only mode continues to enforce the full tenant RBAC policy. Export/Takeout access is restricted to `CLINIC_OWNER` or roles explicitly granted the relevant export permission, with additional authentication and audit as configured. Read-only does not imply unrestricted access to patient or financial data.

# 59. SMS Outbox, OTP, Patient Portal, CMS, Waitlist and Feedback

818. SMS sending is Outbox-backed. Each send request has an idempotent provider/client reference. A definite pre-transmission failure may fail over; a `ReadTimeout` or post-send `5xx` enters `UNKNOWN_PENDING_DELIVERY_CHECK` with a bounded reconciliation TTL. Provider 2 is used automatically only when Provider 1's status API confirms non-acceptance/non-delivery in a way documented by that provider. Otherwise the operation remains ambiguous until reconciliation or an explicitly requested fallback flow after a cooldown. The manual fallback must issue a new OTP generation atomically; it must not reuse or revalidate the prior code.

819. Each OTP challenge binds to normalized phone blind index, purpose, session ID, expiry and generation number. Only an HMAC of the OTP (using a dedicated secret key and challenge/generation context) is stored. Rate limits apply by phone, IP and purpose; failed attempts are bounded; consumption is atomic and one-time. Creating a new generation atomically supersedes the previous one. A delayed old SMS can never authenticate after a newer generation has been created.

820. Proxy booking separates `booker_person_id` from `beneficiary_patient_id`. Booking for a family member does not automatically grant access to that member's historical dossier; access requires the defined relationship/consent/authorization rule. Portal/Bot payloads never include `INTERNAL_STAFF_ONLY` notes, tags or reception alerts. Portal access to appointments, package progress, receipts and patient credits is restricted to the verified patient/authorized guardian context.

821. Clinic CMS supports Draft → Preview → Scheduled/Published, revision history, author audit and managed media storage. Server-side HTML sanitization uses a strict allowlist and removes scripts, inline event handlers, unsafe URLs and disallowed embeds. Sanitization is required on the backend, not only in the editor.

822. Waitlist promotion is an atomic first-claim workflow with idempotency, bounded swap/promotion count (initial maximum one automatic swap unless separately configured), expiry and clear status. Messaging-platform message deletion/revocation is attempted only where the provider actually supports it; otherwise a corrective notification is sent. Waiting-room display masks patient identity according to a privacy rule. Optional 80mm thermal print templates are presentation outputs and do not replace immutable financial records.

823. Post-visit CSAT captures private itemized service/provider ratings for manager analytics. If a clinic enables a public review/social link, the link is shown to all eligible respondents regardless of rating; Review Gating is prohibited. Survey participation/ratings do not control patient eligibility for service or support.

# 60. Clinic Inventory and FEFO Service Consumables (`MOD_INVENTORY`)

824. Inventory is a clinic operational stock ledger, not pharmacy/prescription ERP. Stock changes are recorded as immutable `StockMovement` entries (purchase receipt, service consumption, direct sale if enabled, return, write-off and approved adjustment) linked to `InventoryItem` and, when lot/expiry tracking applies, `InventoryLot`. Manual balance editing is prohibited; corrections use compensating movements.

825. For expiring/lot-tracked items, consumption follows FEFO (First-Expired, First-Out): eligible lots are ordered by earliest valid expiry, then deterministic receipt sequence/ID. Expired, quarantined or recalled lots are excluded from normal consumption. Lot traceability is preserved from purchase receipt through consumption/return/write-off.

826. Optional service consumable templates/BOM define expected item quantities per service. At service completion or the explicitly selected operational trigger, the system creates consumption movements transactionally and snapshots the BOM version and actual deducted lots/quantities. The default behavior on insufficient stock is to block automatic deduction/completion and request manager action; an authorized, audited override or explicit negative-stock policy may be enabled only by a manager. Silent negative stock is prohibited.

827. Inventory movements use integer/scaled quantity rules per item unit, idempotent command handling and concurrency-safe lot balance updates. Returns must identify whether returned stock is reusable, quarantined or written off; they do not automatically re-enter available stock. Inventory reports distinguish on-hand, reserved, consumed, expired, written-off and available quantities. No medicine dispensing, prescription, controlled drug or pharmacy workflow is included.

# 61. Compatibility, Super Admin Operations and Frontend UX

828. Client compatibility metadata is explicit. API requests carry `X-Client-Version`; Sync requests additionally carry `X-Sync-Schema-Version`. Database schema and Outbox event changes follow Expand-and-Contract. Clients below the supported minimum receive a stable upgrade response. Compatibility policy must allow an operationally tested rollout/rollback window and must not break currently supported offline nodes without a migration path.

829. Super Admin operational dashboards show tenant lifecycle, subscription/entitlement status, SMS wallet state, Local Hub heartbeat, Outbox/Inbox lag, client/node versions, backup freshness and restore-test health without default access to patient PII. Support Impersonation requires a support-ticket reference, read-only default, strict TTL, explicit scope and immutable audit of every access/action.

830. Clinic operational panels are desktop-first for reception/management workflows but remain responsive; patient-facing website/portal and SaaS storefront are mobile-first. The presentation boundary uses the Iranian Jalali calendar while persistence and integration timestamps use UTC instants. Displayed dates, numbers and currency use centralized English ASCII digit formatters; input normalization converts Persian/Arabic numerals only in numeric/identifier fields and never rewrites free text. Motion is restrained and respects `prefers-reduced-motion`; loading states use accessible skeletons/spinners and all errors map to the centralized RFC7807-aware notification system.

# Appendix D — Modular Monolith, Repository Structure and Three-Database Boundaries

## D.1 Architectural shape and dependency direction

Each deployable runtime is a Modular Monolith by default. Bounded contexts are modules inside a controlled codebase; they are not separate microservices unless a concrete requirement for scale, isolation, independent release cadence or operational fault containment justifies extraction through an Architecture Change Record.

Each module follows the four-layer dependency direction:

```text
Domain <- Application <- Infrastructure <- Presentation
```

- **Domain:** pure Python entities, value objects, domain events, policies and domain exceptions. It must not import FastAPI, SQLAlchemy, PostgreSQL drivers, Redis, HTTP, Tauri, message SDKs or provider clients.
- **Application:** commands, queries, handlers, policies, ports, DTOs and UoW/transaction coordination. It depends on Domain and abstractions, not concrete persistence/provider adapters.
- **Infrastructure:** Data Mapper mappings, repositories, UoW implementations, PostgreSQL, Outbox/Inbox, cryptography, provider adapters, Redis, filesystem and object-storage adapters.
- **Presentation:** FastAPI routers, request/response schemas, bot adapters and runtime composition roots. It exposes application contracts and does not own business rules.

A module's Domain/Application layers must not import another module's Infrastructure or Presentation. Cross-module communication uses application ports, explicit contracts or approved Domain/Integration Events. SQLAlchemy declarative models remain in Infrastructure; Domain entities do not inherit ORM bases.

## D.2 Three logical PostgreSQL databases

The ecosystem has two logical planes but three independent logical database boundaries:

| Database boundary | Deployment | Authority and contents | Migration/credential boundary |
|---|---|---|---|
| **1. SaaS Control Plane DB** | Cloud-managed PostgreSQL | SaaS customer accounts, tenant lifecycle, plan/module catalog, subscriptions, SaaS billing, SaaS refunds, coupons, affiliate ledger, entitlements, license metadata, contract acceptance, deletion tombstones and platform operations. It must not contain clinic patient dossiers, appointments or treatment records. | Independent CP Alembic lineage; separate database credentials, plane-specific roles/login principals, backup and API boundary. |
| **2. Cloud Tenant Application DB** | Cloud-managed PostgreSQL, normally shared across tenants | Clinic operational data for all Cloud-connected tenants, including cloud-authoritative catalog/RBAC snapshots and online reservations. Every tenant-owned row is scoped by `tenant_id`; composite tenant FKs and RLS are mandatory. | Independent TP Alembic lineage; Tenant Plane `db_app_runtime` and `db_migrator` roles and login principals are separate from Control Plane identities. No Control Plane cross-database FK. |
| **3. Local Hub DB** | PostgreSQL on each clinic Mini PC | Local operational data for that clinic; physical reception operations and approved MANUAL bookings remain authoritative locally while disconnected. It uses the tenant-domain model and approved sync contracts, with explicit local-only metadata where needed. | Tenant migration baseline is applied independently at each node; local credentials and keys are not shared across clinics. No Cloud/Control Plane cross-database FK. |

The Control Plane DB and Cloud Tenant Application DB may be provisioned on the same physical managed PostgreSQL cluster only if the hosting provider supports the required database/role/network isolation. They remain separate logical databases, credentials, migration histories and trust boundaries. Each Local Hub is a separate PostgreSQL instance/database boundary. The Cloud Tenant Application schema may be shared between tenants; Local Hub is normally one tenant per node.

PostgreSQL roles are cluster-wide, not database-local. Therefore, when the two Cloud databases share one physical cluster, one role name cannot represent two independent database-specific roles. In that topology, the Tenant Plane retains the canonical non-login group roles `db_migrator` and `db_app_runtime`; the Control Plane uses the distinct non-login group roles `cp_db_migrator` and `cp_db_app_runtime`. Each plane has its own migration and runtime login principals and credentials. The recommended Cloud login names are `tp_migrator_login`, `tp_app_login`, `cp_migrator_login` and `cp_app_login`. Each independent Local Hub PostgreSQL instance has its own role namespace and may reuse `db_migrator` and `db_app_runtime` with Local-Hub-specific login credentials. These names preserve the duties defined in clauses 744–746; they do not create new application privileges or business boundaries.

On a shared Cloud cluster, database access must be granted per logical database, not inferred from a connection string. Revoke the default `CONNECT` and `TEMPORARY` database privileges from `PUBLIC` on both Cloud databases unless a separately reviewed requirement needs them. Grant `CONNECT` only to the login principals assigned to that database; grant `TEMPORARY` only to an explicitly approved principal if required. Keep schema `USAGE`/`CREATE`, table/sequence privileges, object ownership, and default privileges scoped to the corresponding plane. No runtime login may be a member, directly or transitively, of either plane’s migrator role or the other plane’s runtime role. The CP migration login may assume only `cp_db_migrator`; the Tenant migration login may assume only `db_migrator`. Connection-string separation, network controls and database ACLs are complementary controls; none replaces the others.

There are no cross-database foreign keys. Cross-boundary references use immutable UUIDs, tenant/node identity and versioned API/Integration Event contracts. A successful API call is not a substitute for durable, acknowledged integration delivery.

Public networks must not connect directly to PostgreSQL. The Cloud databases are reachable only through approved application/migration/backup network boundaries. Local Hub accepts only explicitly configured clinic-LAN traffic; TLS is used wherever traffic crosses a trusted local process boundary or network segment.

# Appendix E — Database Provisioning, Alembic Migration Order and Migration Controls

## E.1 Provisioning before Alembic

1. Provision the three logical database boundaries described in Appendix D: Control Plane DB, Cloud Tenant Application DB and each Local Hub DB.
2. PostgreSQL roles are cluster-wide. Create non-login group/ownership roles once per PostgreSQL cluster, not once per logical database. If the Cloud Control Plane DB and Cloud Tenant Application DB share a cluster, use `db_migrator` and `db_app_runtime` for the Tenant Plane and the distinct roles `cp_db_migrator` and `cp_db_app_runtime` for the Control Plane. Each independent Local Hub PostgreSQL instance has its own role namespace and may use `db_migrator` and `db_app_runtime`.
3. Create separate narrowly scoped login principals for each plane and purpose. For a shared Cloud cluster, the recommended names are `tp_migrator_login`, `tp_app_login`, `cp_migrator_login` and `cp_app_login`. Runtime principals inherit only their own plane’s runtime group role; they must never be members, directly or transitively, of a migrator role or the other plane’s runtime role.
4. Migrator group roles are `NOLOGIN` and own only the schemas/tables belonging to their database boundary. The migration login may assume only its corresponding migrator role and only in a controlled CI/deployment migration job. Migration credentials are not placed in application/worker runtime container images, secrets or environment.
5. No runtime principal is `SUPERUSER`, has `BYPASSRLS`, owns tenant tables, has `TRUNCATE`, or has schema `CREATE`, DDL or policy-management permissions. Grant only the required schema `USAGE`, table DML and sequence privileges. Configure default privileges so future objects created by a plane’s migrator do not accidentally grant access to another plane or to `PUBLIC`.
6. Revoke database `CONNECT` and `TEMPORARY` privileges from `PUBLIC` on the two Cloud databases unless a separately reviewed requirement needs them. Grant `CONNECT` only to the login principals assigned to that database. Grant `TEMPORARY` only to an explicitly approved principal if required. Verify effective privileges rather than relying on connection-string separation.
7. Create least-privilege backup/restore identities separately; they are not ordinary application query roles and must not be shared with runtime or migration logins.
8. Verify the PostgreSQL version/extension support. PostgreSQL 15 is the baseline test database (clause 349); `btree_gist` must be installed and verified before appointment exclusion migrations.
9. Keep Tenant Plane and Control Plane migration connection strings, secrets, login principals, Alembic environments and version tables separate.
10. Verify plane isolation using actual non-superuser login credentials: negative connection tests across the two Cloud databases, role-membership checks (including transitive membership), schema/object privilege checks, and confirmation that runtime logins cannot assume any migrator role. Do not use a superuser/table-owner session as evidence of runtime isolation.

### Minimum non-production Testcontainers topology

The minimum representative topology uses **two PostgreSQL 15 Testcontainers instances**:

- **Cloud PostgreSQL container:** one cluster hosting two logical databases, the SaaS Control Plane DB and the Cloud Tenant Application DB. The test provisions plane-specific role groups and login principals, separate database ACLs, separate Alembic environments and separate migration version tracking.
- **Local Hub PostgreSQL container:** a second, independent PostgreSQL instance representing one clinic Mini PC. It hosts the Local Hub DB, uses the Tenant Plane migration lineage independently, and has its own connection credentials and cluster-wide role namespace.

Three logical databases inside one PostgreSQL container are not a sufficient topology test because that would not represent the independent Local Hub PostgreSQL instance required by Appendix D.2. A second Local Hub container is not part of the minimum M0 topology; multi-node Sync, collision and distributed failure tests belong to later implementation milestones. The same `TP0001` revision is applied independently to the Cloud Tenant DB and Local Hub DB. The CP Alembic environment and version tracking are independently targeted at the Control Plane DB and must not be changed by Tenant Plane migrations. Testcontainers must verify actual role connection denials and plane-local privileges. Static configuration checks may supplement, but must not replace, the real PostgreSQL role tests.

## E.2 Tenant Plane migration lineage (TP0001–TP0007)

This tenant migration lineage is applied independently to the Cloud Tenant Application DB and each Local Hub DB. The initial schemas may share the same baseline to reduce drift; any Local/Cloud divergence must be explicit, versioned and tested. Migration IDs and ordering must remain deterministic across environments.

For `TP0001`, the phrase “common constraints” is limited to the constraints explicitly shown for `tenant_registry` in Appendix F.2. It does not authorize additional tables, columns, indexes, triggers, policies or lifecycle behavior. `TP0001` installs/verifies `btree_gist` and creates only the `tenant_registry` root defined in F.2. RLS remains in `TP0007` by default. If a later implementation explicitly enables RLS earlier on any table, the migration-only permissive policy required by clause 746 must be created in the same migration before a subsequent migration needs access.

The UUIDv7 strategy is fixed at the application level by clauses 45–46; the Python runtime version and concrete UUIDv7 provider are not fixed by this specification. Python’s standard-library `uuid.uuid7()` is available starting with Python 3.14, not Python 3.13. This fact does not mandate Python 3.14 or select a third-party provider (Python 3.14 documentation: `https://docs.python.org/3.14/library/uuid.html`). Pin the supported Python runtime and verify Local Hub, Cloud Hub, worker and test-environment compatibility before selecting the provider. TP0001 schema acceptance is separate from application-provider acceptance: the database column must have no UUID-generating default; application UUIDv7 generation/insertion tests are required when the approved provider is selected and before application code relies on it. No database function may be used as a substitute.

| Migration | Scope | Required invariants / verification |
|---|---|---|
| `TP0001` — Extensions and tenant root | Verify PostgreSQL compatibility; install/verify `btree_gist`; create `tenant_registry` and common constraints. | App-generated UUIDv7 only; no database UUID default that bypasses the application policy. |
| `TP0002` — Person identity and PII | Create `tenant_persons`, `person_identifiers`, `person_phones`, `patient_profiles`, `staff_profiles`, `user_accounts`. | Direct tenant root FKs; composite tenant FKs; optional identifiers; AES-GCM nonce/tag/key/AAD versions; HMAC active/next; shared-phone support. |
| `TP0003` — Governance and RBAC | Create `tenant_governance_assignments`, `tenant_roles`, `role_permission_assignments`, `user_role_assignments`, permission catalog snapshot structures. | Separate staff/provider existence from login accounts; doctor/specialist may have staff profile without a login; Cloud policy is authoritative. |
| `TP0004` — Services and atomic resources | Create `services`, `bookable_resources`, `service_resource_requirements`. | Direct tenant root FKs; composite tenant FKs; `quantity_required > 0`; specific resource must belong to same tenant and match required resource type (domain invariant/trigger plus tests). |
| `TP0005` — Appointment and multi-resource allocation | Create `appointments`, `appointment_resource_allocations`, and `hold_expiry_work_items`/lease metadata if used. | Beneficiary references `patient_profiles`; optional booker references `tenant_persons`; bounded half-open range; channel/pool CHECK; ONLINE-only partial GiST EXCLUDE; MANUAL remains outside predicate; worker uses queue-claim then global lock order. |
| `TP0006` — UoW consistency infrastructure | Create `idempotency_records`, `outbox_messages`, `inbox_messages`, `sync_stream_counters`, `audit_entries` and required node/sync metadata. | Unique operation identity/fingerprint; durable sequence; Outbox lease ownership; Inbox duplicate protection; append-only audit grants. |
| `TP0007` — Tenant RLS and grants | Enable and FORCE RLS for every tenant-owned table in shared Cloud DB; create runtime base/guard and migration-only policy; apply exact SQL grants. | `db_migrator` owner access under its explicit policy; `db_app_runtime` tenant guard; no role inheritance to migrator; no runtime TRUNCATE/DDL; fail-closed missing context. |

`TP0007` must be ordered after the necessary schema/table creation and data migrations so that controlled migration jobs can still access/transform data under the `db_migrator` policy. If RLS is enabled earlier on a table, the migration policy must be created in the same migration before the next data migration requires access. The ordering and role grants are verified in migration integration tests.

## E.3 Control Plane migration lineage (CP0001–CP0008)

Control Plane migrations run in a separate Alembic environment/database and must never create a foreign key to a Tenant Plane database. Cross-plane references use immutable UUIDs and versioned API/event contracts.

The Control Plane Alembic environment, connection configuration and version table are independent from the Tenant Plane lineage. During initial bootstrap, the CP environment and its version-table tracking may be initialized and verified without creating CP0001 business tables. If no CP business revision is yet defined, do not invent CP0001 columns or constraints. A supported Alembic version-table initialization mechanism may be used; a no-op technical baseline revision is optional only if required by the selected tooling and must not be represented as CP0001. A migration history row or technical baseline does not imply that any Control Plane business schema has been implemented. Tenant Plane migrations must never connect to or modify the CP database, and vice versa.

| Migration | Scope |
|---|---|
| `CP0001` — SaaS account and tenant lifecycle root | `saas_customer_accounts`, Control Plane `tenants`, ownership/administration assignments and tenant lifecycle states |
| `CP0002` — Plans and entitlements | Subscription plans, plan modules, tenant subscriptions, entitlement snapshots and module proration policy metadata |
| `CP0003` — Contract acceptance | Versioned agreement references, content hash and `ContractAcceptanceRecord` |
| `CP0004` — Nodes and licenses | Node registration, public-key metadata, key status, `LicenseLeaseToken`/lease metadata and re-bind operations |
| `CP0005` — Erasure and deletion orchestration | Independent `tenant_erasure_tombstones`, deletion approvals, Cloud/local deletion states and restore guard metadata |
| `CP0006` — SaaS billing | SaaS invoices, payment attempts, verified receipts, subscription refunds and commercial adjustments |
| `CP0007` — Affiliate ledger | Affiliate attribution, append-only commission ledger, cumulative refund/clawback projections and payouts |
| `CP0008` — SMS wallet and platform notifications | SMS wallet/accounting, platform notification policy and dispatch metadata |

## E.4 Expand-and-contract and migration discipline

- Do not create one giant initial migration. Each migration is additive, reviewable and independently testable.
- Use Expand-and-Contract for API, schema and Outbox event evolution. Deploy code able to tolerate old/new representations before destructive contract migrations.
- Run `CREATE INDEX CONCURRENTLY` only in a dedicated Alembic non-transactional/autocommit block. After failure, inspect `pg_index.indisvalid`; drop invalid indexes only after diagnosing the cause, then retry.
- Backfills are idempotent, batched, observable and resumable. They use deterministic checkpoints and never silently discard conflicting data.
- A migration's `downgrade` policy must be explicit. Irreversible data transformations require a forward-fix/restore plan rather than a fake destructive downgrade.
- Test migration from an empty database and from the immediately prior schema version. Test both Cloud Tenant and Local Hub deployment topologies.
- RLS policies/grants are provisioned as code and verified with actual role identities; never run tenant isolation acceptance tests solely as PostgreSQL superuser/table owner.
- UUIDv7 IDs are generated by application code/approved ID provider, not by arbitrary database defaults.


`MATCH SIMPLE` on `specific_resource_id` is deliberate: `tenant_id` stays non-NULL and is independently checked against `tenant_registry`, while a NULL `specific_resource_id` means the requirement may be satisfied by any compatible resource in the group. ## F.4 Appointment and multi-resource allocation schema

```sql
CREATE TABLE appointments (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES tenant_registry(tenant_id),
    beneficiary_patient_id UUID NOT NULL,
    booker_person_id UUID NULL,
    patient_booking_note TEXT NULL,
    service_id UUID NOT NULL,
    status VARCHAR(32) NOT NULL,
    booking_channel VARCHAR(32) NOT NULL
        CHECK (booking_channel IN ('ONLINE_WEB', 'ONLINE_BOT', 'MANUAL_STAFF')),
    capacity_pool VARCHAR(16) NOT NULL
        CHECK (capacity_pool IN ('ONLINE', 'MANUAL')),
    scheduled_start_at_utc TIMESTAMPTZ NOT NULL,
    scheduled_end_at_utc TIMESTAMPTZ NOT NULL,
    hold_expires_at_utc TIMESTAMPTZ NULL,
    aggregate_version BIGINT NOT NULL CHECK (aggregate_version > 0),
    created_at_utc TIMESTAMPTZ NOT NULL,
    updated_at_utc TIMESTAMPTZ NOT NULL,
    CONSTRAINT ck_appointment_valid_time
        CHECK (scheduled_start_at_utc < scheduled_end_at_utc),
    CONSTRAINT ck_appointment_patient_booking_note_length
        CHECK (patient_booking_note IS NULL OR char_length(patient_booking_note) <= 2000),
    CONSTRAINT ck_appointment_channel_pool CHECK (
        (booking_channel IN ('ONLINE_WEB', 'ONLINE_BOT') AND capacity_pool = 'ONLINE')
        OR (booking_channel = 'MANUAL_STAFF' AND capacity_pool = 'MANUAL')
    ),
    CONSTRAINT fk_appointment_beneficiary_patient_tenant
        FOREIGN KEY (tenant_id, beneficiary_patient_id)
        REFERENCES patient_profiles (tenant_id, id) MATCH FULL,
    CONSTRAINT fk_appointment_booker_person_tenant
        FOREIGN KEY (tenant_id, booker_person_id)
        REFERENCES tenant_persons (tenant_id, id) MATCH SIMPLE,
    CONSTRAINT fk_appointment_service_tenant
        FOREIGN KEY (tenant_id, service_id)
        REFERENCES services (tenant_id, id) MATCH FULL,
    CONSTRAINT uq_appointment_tenant_id UNIQUE (tenant_id, id)
);

CREATE TABLE appointment_resource_allocations (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES tenant_registry(tenant_id),
    appointment_id UUID NOT NULL,
    resource_id UUID NOT NULL,
    booking_channel VARCHAR(32) NOT NULL,
    capacity_pool VARCHAR(16) NOT NULL,
    allocation_status VARCHAR(32) NOT NULL,
    time_slot TSTZRANGE NOT NULL,
    created_at_utc TIMESTAMPTZ NOT NULL,
    CONSTRAINT fk_allocation_appointment_tenant
        FOREIGN KEY (tenant_id, appointment_id)
        REFERENCES appointments (tenant_id, id) MATCH FULL,
    CONSTRAINT fk_allocation_resource_tenant
        FOREIGN KEY (tenant_id, resource_id)
        REFERENCES bookable_resources (tenant_id, id) MATCH FULL,
    CONSTRAINT ck_allocation_bounded_half_open CHECK (
        NOT isempty(time_slot)
        AND NOT lower_inf(time_slot)
        AND NOT upper_inf(time_slot)
        AND lower_inc(time_slot)
        AND NOT upper_inc(time_slot)
        AND lower(time_slot) < upper(time_slot)
    ),
    CONSTRAINT ck_allocation_channel_pool CHECK (
        (booking_channel IN ('ONLINE_WEB', 'ONLINE_BOT') AND capacity_pool = 'ONLINE')
        OR (booking_channel = 'MANUAL_STAFF' AND capacity_pool = 'MANUAL')
    ),
    CONSTRAINT uq_allocation_one_resource_per_appointment
        UNIQUE (tenant_id, appointment_id, resource_id),
    CONSTRAINT uq_allocation_tenant_id UNIQUE (tenant_id, id),
    CONSTRAINT ex_online_resource_time
        EXCLUDE USING gist (
            tenant_id WITH =,
            resource_id WITH =,
            time_slot WITH &&
        ) WHERE (
            capacity_pool = 'ONLINE'
            AND allocation_status IN ('PENDING_PAYMENT_HOLD', 'CONFIRMED', 'CHECKED_IN')
        )
);
```

`beneficiary_patient_id` always references an actual `patient_profiles` row; a general `tenant_persons` record is not enough to receive an appointment as a patient. `booker_person_id` is optional and may refer to any person allowed to book on behalf of the beneficiary. It is intentionally `MATCH SIMPLE` because the booker may be absent while `tenant_id` remains non-NULL. The Local/Cloud ownership and sync rules continue to determine which hub may create or confirm each channel.

## F.5 Hold expiry work queue template

The queue is optional as a separate persistence construct, but if used, it must be independent from the parent Appointment lock used by the business UoW. A minimal starting template is:

```sql
CREATE TABLE hold_expiry_work_items (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL REFERENCES tenant_registry(tenant_id),
    appointment_id UUID NOT NULL,
    due_at_utc TIMESTAMPTZ NOT NULL,
    work_state VARCHAR(24) NOT NULL
        CHECK (work_state IN ('PENDING', 'CLAIMED', 'DONE', 'RETRYABLE', 'NOOP')),
    claim_token UUID NULL,
    claimed_by TEXT NULL,
    lease_expires_at_utc TIMESTAMPTZ NULL,
    attempt_count INTEGER NOT NULL DEFAULT 0 CHECK (attempt_count >= 0),
    created_at_utc TIMESTAMPTZ NOT NULL,
    updated_at_utc TIMESTAMPTZ NOT NULL,
    CONSTRAINT fk_hold_work_appointment_tenant
        FOREIGN KEY (tenant_id, appointment_id)
        REFERENCES appointments (tenant_id, id) MATCH FULL,
    CONSTRAINT uq_hold_work_appointment UNIQUE (tenant_id, appointment_id)
);

CREATE INDEX ix_hold_expiry_due_work
ON hold_expiry_work_items (due_at_utc, id)
WHERE work_state IN ('PENDING', 'RETRYABLE');
```

A worker may `SELECT ... FOR UPDATE SKIP LOCKED` only on `hold_expiry_work_items` to claim a work item and lease. It commits that claim, starts a new scheduling UoW, then locks Resource → Appointment → Allocation and revalidates. A claim token/lease prevents stale workers from completing a replaced claim. Do not use `SKIP LOCKED` on Appointment during the claim phase.

## F.6 RLS and role policy template including migration maintenance

```sql
ALTER TABLE appointments ENABLE ROW LEVEL SECURITY;
ALTER TABLE appointments FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_runtime_base ON appointments
AS PERMISSIVE FOR ALL TO db_app_runtime
USING (true) WITH CHECK (true);

CREATE POLICY tenant_runtime_guard ON appointments
AS RESTRICTIVE FOR ALL TO db_app_runtime
USING (
    tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
)
WITH CHECK (
    tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
);

-- Applies because FORCE ROW LEVEL SECURITY also subjects the table owner.
CREATE POLICY tenant_migrator_maintenance ON appointments
AS PERMISSIVE FOR ALL TO db_migrator
USING (true) WITH CHECK (true);
```

At the start of every Tenant Application Plane UoW, after verifying the caller's JWT, Sync node identity or signed internal job envelope, bind the context inside the local transaction:

```sql
SELECT set_config('app.current_tenant_id', :verified_tenant_id, true);
```

The migration policy does not replace SQL grants; it only supplies an applicable RLS policy to the migration role. Runtime accounts must not inherit `db_migrator`. Runtime tests use the actual Tenant Plane `db_app_runtime` login/role, and migration tests use the separate Tenant Plane migration principal. On a shared Cloud cluster, the Control Plane uses its distinct `cp_db_migrator` and `cp_db_app_runtime` role groups; the Tenant Plane RLS policies in this template must not be silently retargeted to a shared cross-plane role. Each independent Local Hub instance may use the canonical Tenant Plane role names in its own PostgreSQL cluster. The pattern applies to every tenant-owned table where these roles apply, not just `appointments`.

## F.7 Phase 1 acceptance checklist

### Database and tenant isolation

- [ ] Runtime role is not table owner, `SUPERUSER` or `BYPASSRLS`.
- [ ] Runtime principal is not a member of `db_migrator`; migration credentials are absent from runtime containers/images.
- [ ] `db_app_runtime` has no `TRUNCATE`, DDL, ownership or policy-management privileges.
- [ ] `db_migrator` can run authorized migrations under the migration-only RLS policy while `FORCE ROW LEVEL SECURITY` is active.
- [ ] Missing tenant GUC sees/writes zero tenant rows (fail closed).
- [ ] Tenant A cannot `SELECT`, `INSERT`, `UPDATE`, `DELETE` or attach FKs to Tenant B rows.
- [ ] Root tables reject unknown tenant IDs through `tenant_registry` foreign keys.
- [ ] Mandatory composite FKs use non-NULL references; nullable composite relationships explicitly use `MATCH SIMPLE`.
- [ ] Tests run under the actual Tenant Plane runtime login/role, not superuser or migration role.

### Shared Cloud cluster plane isolation

- [ ] On a shared Cloud PostgreSQL cluster, Tenant Plane and Control Plane use distinct cluster-wide non-login role names and separate login principals; Local Hub may reuse Tenant Plane group-role names only because each Local Hub is a separate PostgreSQL instance.
- [ ] `CONNECT` and `TEMPORARY` are revoked from `PUBLIC` on the Cloud Control Plane and Cloud Tenant databases unless explicitly required and documented.
- [ ] Only the intended plane-specific login principals can `CONNECT` to each Cloud database; the Tenant runtime and migrator logins cannot connect to the Control Plane DB, and the Control Plane runtime and migrator logins cannot connect to the Tenant DB.
- [ ] Runtime logins inherit only their own plane’s runtime role and have no direct or transitive membership in any migrator role or the other plane’s runtime role.
- [ ] Each migrator login can assume only its corresponding plane-specific `NOLOGIN` migrator role in a controlled migration job; it cannot connect to the other plane’s database.
- [ ] Schema, table, sequence and default privileges are limited to the owning plane; cross-plane runtime logins cannot use or mutate the other plane’s objects.
- [ ] Negative connection/privilege tests use the actual non-superuser login credentials; `has_database_privilege`/role-membership inspection alone is supplemented by attempted real connections.
- [ ] Control Plane and Tenant Plane Alembic environments use distinct database targets and independent version tables; neither lineage advances or mutates the other’s database.

### Identity and cryptography

- [ ] Creating a patient without National ID succeeds.
- [ ] Creating staff without National ID succeeds.
- [ ] A doctor/specialist may have a staff profile without a `user_accounts` login.
- [ ] The staff form exposes the permission-protected `Create login account` opt-in for all staff/provider types; it is off by default and does not auto-grant RBAC permissions.
- [ ] `user_accounts` DDL, tenant/person composite FK, one-account-per-person constraint and tenant-unique login identifier are present and migration-tested.
- [ ] Two family members may share one phone blind index.
- [ ] Raw ID/phone values are not present in database plaintext columns or logs.
- [ ] AES-GCM AAD mismatch/ciphertext transplant fails authentication.
- [ ] HMAC dual-write/backfill/cutover and rollback behavior is tested with concurrent writes.

### Catalog and scheduling

- [ ] Service and resources for an unknown `tenant_id` are rejected.
- [ ] A requirement's specific resource must belong to the same tenant and match the expected resource type.
- [ ] `beneficiary_patient_id` cannot reference a general person without a patient profile.
- [ ] Optional `booker_person_id` may be NULL and, when present, must be same-tenant.
- [ ] `patient_booking_note` is nullable, length-limited, audit-attributed and not confused with internal staff/clinical notes.
- [ ] Portal/API tests prevent one patient from reading another patient's booking note.
- [ ] Adjacent ranges `[09:00,09:30)` and `[09:30,10:00)` both succeed.
- [ ] Overlapping ONLINE allocations for the same resource fail with exclusion violation `23P01`.
- [ ] Online website and bot contend on the same ONLINE pool.
- [ ] MANUAL may overlap ONLINE and MANUAL only with permission, acknowledgement, current conflict snapshot and immutable audit.
- [ ] Manual sync retains MANUAL channel/pool and does not cancel Cloud ONLINE reservations.
- [ ] Required resource groups cannot be omitted.
- [ ] Expired holds do not remain stuck; worker claims work items separately then locks Resource → Appointment → Allocation.
- [ ] Hold worker, inline booking and payment callback races are exercised with concurrent PostgreSQL transactions.
- [ ] Late callbacks never cancel a competing confirmed ONLINE appointment.

### Payment and affiliate

- [ ] CASH receipts require operator/shift/permission and do not require a bank destination account by default.
- [ ] POS receipts require a managed `pos_terminal_id` and terminal reference/state.
- [ ] CARD_TO_CARD receipts require destination account and verified bank reference/settlement evidence.
- [ ] ONLINE receipts require server-to-server verification and merchant/order/amount/currency/provider-reference matching.
- [ ] Screenshot-only claims remain `UnverifiedPaymentClaim` and do not enter collection reports.
- [ ] Affiliate partial refunds use cumulative rounding; full cumulative refund claws back exactly the original commission with no Rial drift.

### Infrastructure and restore

- [ ] Each HTTP request/concurrent task gets a fresh `AsyncSession`/UoW.
- [ ] Same idempotency identity/fingerprint replays; different fingerprint conflicts; concurrent requests do not execute twice.
- [ ] Outbox event commits atomically with business state.
- [ ] Duplicate Inbox delivery is harmless; sequence progress is durable/resumable.
- [ ] Tenant erasure tombstones are independently recoverable and applied before traffic after restore.
- [ ] Production restore tests validate the full Cloud/Control Plane/Object Storage recovery sequence before Gate D.

A checklist item is not complete merely because it appears here. Attach the migration ID, test name/result, environment/version and evidence reference to the corresponding Open Item/release record.
