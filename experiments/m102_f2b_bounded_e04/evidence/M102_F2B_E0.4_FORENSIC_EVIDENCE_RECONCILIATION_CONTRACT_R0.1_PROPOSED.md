## 5. E0.4 corrective acceptance protocol

### 5.1 C01 lifecycle without circular self-dependency

The design must avoid both the historical ordering bug **and** falsely publishing C01 as `OBSERVED_PASS` while integrity checks are pending. The exact implementation may vary, but the following invariant-preserving sequence is mandatory:

1. Generate evidence from all test/control cases, including the appropriate **provisional** C01 record at a state such as `UNVERIFIED` if the final integrity pass has not yet happened; do not claim it is accepted. The record's `case_id` and path must already be correct.
2. Verify the **other 18** files and a **candidate final C01 payload** in memory against complete schema/provenance/redaction/path checks, with trusted actual CI identity inputs. No success solely because the `REQUIRED_CASE_IDS` list was shortened.
3. Finalize C01 **only after** the intended checks can be satisfied. Materialize all **19** stable, complete JSON byte streams (including finalized C01). Produce an external SHA-256 manifest over those **finished** bytes; never include a file's own digest inside that file. If any result changes later, regenerate the manifest and invalidate previous verification.
4. Independently re-read **all 19** JSONs plus the separately written digest manifest from disk, using a fresh verifier invocation whose result gates the job. Validate each file's raw bytes against its own manifest entry, its full provenance, safe references, classification and redaction checks. Confirm exact counts: 19 required, 19 present, 19 unique entries, no unexpected case file or skip-as-pass.
5. On any failure, leave the CI job **red** and preserve truthful diagnostics (`OBSERVED_FAIL`, `BLOCKED`, or `UNVERIFIED` as applicable); never publish contract acceptance from provisional green pytest. The final independent report must reconcile any intermediate status with the last verified stable bytes. An apparent C01 PASS inside a failed pipeline is **not** sufficient contractual acceptance.
6. After pytest/JUnit/log finalization, include any mandatory additional raw evidence in a separately finalized digest inventory or produce an explicitly layered second manifest. Exclude the manifest(s) themselves, volatile GitHub-generated URLs and the later consolidated report from the lists they hash, and explicitly document these exclusions. The final report records the verified SHA-256 of the stable manifest and references independent CI artifact identifiers; its own digest is not part of that manifest.

**Anti-circularity rule:** no JSON embeds the digest of itself, no manifest lists its own SHA-256, no expected digest is copied from an unverified claim and then deemed independent, and no final report states C01 accepted until the post-finalization validator has independently recomputed and checked every manifest hash.

### 5.2 Trusted provenance versus self-reported fields

For a GitHub Actions run, the validator must compare case JSON values to **independent, real runner context**:

- `tested_commit_sha` must be a full 40-hex commit and equal both `git rev-parse HEAD` and verified `GITHUB_SHA` (or an equivalently trusted immutable CI checkout source). Never accept `LOCAL_UNKNOWN` as a CI SHA.
- `run_id` must be the exact numeric `GITHUB_RUN_ID`, validated as such and later corroborated against the actual GitHub Actions run. Never accept `LOCAL_NOT_CI` as a CI run ID. Record the CI attempt separately; distinguish two different run IDs from a manual rerun of one run.
- `parent_e02_final_commit_sha`, approved contract hash, source version, branch and CI event must match independently verified pinned values; record the E0.3 final evidence parent and any copy provenance separately to avoid confusing them with E0.2 lineage.
- `timestamp_utc` must parse as a timezone-aware ISO 8601 timestamp normalized to UTC, with plausible run-window boundaries; record observed clock skew instead of inventing timestamps.
- `postgres_server_version_num`, DB label, session/current roles and actual SQL/catalog outputs must come from the current synthetic run for physical proofs; for governance controls, explicit `NOT_APPLICABLE` plus reason is required. Do not substitute synthetic example `150020` as a claimed future result.
- Repository-relative evidence paths must be canonical, must stay under the E0.4 evidence allowlist, must not traverse out, must not be absolute, symlinked or duplicate under case folding, must exist and must correspond to real artifacts. Missing external metadata -> `UNVERIFIED`, not a fabricated match.

**Trust model:** a manifest generated by the same suite provides tamper detection across stored bytes, but is **not an independent signature** and cannot establish that the generating code was honest. That requires immutable GitHub run metadata, source hashes, artifact verification and a separate read-only reviewer. Do not describe SHA-256 alone as proof of human identity or independent authorization.

### 5.3 Evidence schema, semantic validation and redaction

Retain **every** required field of E0.3 §6.2: `case_id`, `finding_id`, `classification`, `execution_kind`, `contract_sha256`, `parent_e02_final_commit_sha`, `tested_commit_sha`, `run_id`, `timestamp_utc`, `postgres_server_version_num`, `database_label`, `session_user`, `current_user`, `preconditions`, `command_redacted`, `expected_result`, `observed_result`, `exit_code`, `before_state`, `after_state`, `evidence_files`, `limitations`.

Additionally reject: wrong field types and `null` where not allowed; unexpected/duplicated IDs; `SKIPPED` as pass; false `OBSERVED_PASS` inconsistent with expected/observed/exit values; wrong finding or execution kind; empty results disguised as strings; no source/test linkage; a schema-only pass with failed forensic checks; invalid/missing manifest entries; stale run ID/SHA; off-allowlist reference; missing artifacts; user-provided strings masquerading as trusted runner provenance. Explicit not-applicable values require an explanatory reason and cannot replace any mandatory PG proof.

Treat contents of `command_redacted`, SQL error text, DSNs, environment snippets and catalog outputs as potentially sensitive. Use deny-pattern checks for common secrets, credentials, patient identifiers and live DSNs; also manually review representative evidence and CI logs because regular expressions are not a completeness proof. On a detected leak, stop and sanitize **future new** artifacts under the new grant without editing historical records. Do not retain a live secret in evidence even for debugging. Redaction must preserve falsifiable relevant SQLSTATE/catalog outcomes.

### 5.4 Digest manifest and verification

A separate deterministic `EVIDENCE_SHA256SUMS.txt` (or equivalent strict manifest) must enumerate the **exact final bytes** of all 19 case JSON files, with canonical relative paths and lower-case 64-hex SHA-256. Optional raw logs/JUnit/provenance artifacts may be in the same manifest **only after written and stable**, otherwise list them in a clearly identified later immutable layer. For each declared entry: open safely, compute SHA-256 of actual bytes, compare, detect missing/extra/duplicate/case-collision entries, reject `..`/symlinks/non-regular files, and require the expected 19 files. Manifest creation and **separate read-back verification** are distinct observable events; verify their return codes and store their outputs in non-self-hashed evidence. The final report must include the stable manifest's real digest and independent GitHub artifact metadata, not just a self-asserted `schema_errors=[]`.
