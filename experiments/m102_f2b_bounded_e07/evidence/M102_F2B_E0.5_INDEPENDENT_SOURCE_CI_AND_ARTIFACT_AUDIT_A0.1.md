## 3. Independent findings (source-grounded)

### E5A-01 — HIGH — trusted contract/lineage identity is incomplete (CONFIRMED)

**Contract:** E0.5 §6 `E05-FC03`; §6.2; D0.1 §§2, 7.  
**Tested source:** `harness/evidence.py:30–57,169–198,263–295`.

`write_evidence()` records `authorization_sha256` and `parent_e04_tested_commit_sha` (`:178–184`), but `REQUIRED_FIELDS` does not require them (`:30–57`), and `validate_evidence_record()` checks only the contract, E0.2 parent, E0.3 final parent and E0.4 final parent (`:287–294`); it never matches the approved D0.1 SHA nor the E0.4 tested SHA. It also does not validate `e03_contract_sha256_historical` or `e04_contract_sha256_historical`. Consequently a current-run JSON with a freshly recomputed valid primary manifest could carry fabricated/missing authorization or tested-lineage fields and still pass those specific checks. This is **a provable validator coverage gap**, not a claim that the actual 19 CI records were fabricated; the actual artifact records match the cited current-run SHA/run.

**Required closure:** exact required-field and value checks for every approved digest and lineage link; mandatory trusted GitHub context on acceptance; positive and negative controls using the real final entrypoint, independent externally read GitHub identity evidence.

### E5A-02 — HIGH — semantic types, UTC and self-owned evidence paths do not meet FC04/FC05 (CONFIRMED)

**Contract:** `E05-FC04`, `E05-FC05`, §6.3.  
**Tested source:** `harness/evidence.py:234–261,296–335,304–315,380–387`.

- The timestamp validator accepts **any timezone-aware offset**, not exclusively UTC (`datetime.fromisoformat()` and `tzinfo is not None`); it does not check zero UTC offset.
- Numeric types are converted with `int()` (`:319–323`); `150020` provided as a string would be accepted, rather than enforcing a strict data type. The passing `exit_code` accepts string `"0"` (`:255–258`). Nonempty `observed_result` is checked but its intended object type is not enforced; generic `before_state`/`after_state` are not necessarily meaningful case-specific proof.
- `evidence_files` only needs a list of strings under a prefix; the verifier does **not** require each case to refer to its own canonical evidence file nor independently validate every referenced file's actual existence and canonical resolution (`:304–315`). The primary-manifest verified paths themselves receive stronger checks and were valid in this artifact, but **that does not close the linked-path predicate**.
- `source_test` merely needs to be nonblank (`:334–335`); the trusted origin test is not verified against the exact JUnit function identity.

**Required closure:** reject wrong data types, non-UTC-offset values and contradictory per-case proofs; require exact `case_id` ↔ `evidence_files` ownership and canonical regular-file path checks; bind `source_test` to trusted expected function identity. Preserve legitimate negative-SQL exit-code semantics instead of universally forcing zero.

### E5A-03 — HIGH — prescribed falsifiability/negative controls lack full real-gate evidence (CONFIRMED)

**Contract:** E0.5 §5 `E04-V03/V04/V11/V13/V14`; §§6–7 `E05-FC07`, `E05-FC08`, with *positive + negative controls for every predicate* and evidence of actual invoked command/exit.  
**Tested source:** `tests/test_z_e04_validator_fixtures.py:170–220,324–360,436–445,481–549`; `scripts/ci_gate_sequence.py:16–41`.

- `V03`, `V04` and the status check in `V08` now **correctly call the real `verify_case_manifest()`** against disposable, tampered trees. That is a genuine improvement over E0.4. However they assert returned error lists, **not actual nonzero CLI/process exit** for each fault as the contract requires; their fixture records show `exit_code=0` for the *passing pytest fixture*, not the rejected verifier process. The two exit types must not be conflated.
- `V13` invokes a distinct disposable CLI `ci_gate_sequence.py` with `--pytest-rc 0` and obtains a nonzero process result. This demonstrates a job-equivalent fail-closed path for a byte mismatch, **but** it explicitly uses `--require-acceptance 0` at `test_z_e04_validator_fixtures.py:499–514`, while the mandatory real CI post-pytest verifier calls `verify_case_manifest(require_acceptance_pass=True)` at `scripts/post_pytest_forensic_verify.py:42–47`. It does not constitute an end-to-end provider job failure test, nor exactly the same acceptance options. The negative condition still correctly produces an error.
- `V11` only tests a damaged **primary** manifest, not negative/duplicate/self-hash/stale behavior of the newly introduced **auxiliary** manifest. `write_auxiliary_manifest`/`verify_auxiliary_manifest` were used positively, but no separate source-grounded auxiliary tamper denial/exit proof is present in the 32 collected tests.
- `V14` has removed the former `or True` and now requires the real primary manifest and positive verification (`:529–537`). This specific E0.4 flaw **is closed**; do not re-report it as still present.

**Required closure:** drive positive + negative cases through the same final acceptance CLI/options (or justify exact equivalence) and record expected/actual nonzero exit values per predicate. Specifically exercise auxiliary digest substitution, missing/duplicate/self-hash, stale sidecars and nested tamper; avoid introducing extra database semantics.

### E5A-04 — HIGH — E05-FC01..FC10 individual positive/negative evidence not established (CONFIRMED)

**Contract:** E0.5 §6 explicitly demands, *for each* `E05-FC01` through `E05-FC10`, a positive control, at least one negative/tamper control exercising the real entrypoint, and a machine-readable result linked to the current CI identity; D0.1 §§7, 10 require every `E05-FC*` result in the final report.

Original artifact inventory contains **19 E03 JSON**, **14 E04-V JSON**, JUnit/logs/manifests, but **no separate machine-readable E05-FC01..FC10 verdict matrix or per-predicate results with both positive and negative process outcomes**. The final report §7 simply asserts all ten were enforced without listing their measured test outcomes; the original `junit.xml` contains only the preserved 18 E03 + 14 E04 test functions. A single fixture could potentially support several predicates **if an explicit, exact, independently verifiable cross-reference ledger** documented the positive/negative evidence and exits; that required link is not in the original artifact/report. Lack of separate FC-named pytest tests alone is not necessarily a defect; **absence of the demanded auditable mapping and measured results is**.

**Required closure:** produce a schema-checked E05-FC01..FC10 result inventory and mapping to original JUnit names, actual tested command, positive result, tamper result, exit, case/fixture evidence, SHA/run and both manifest seals. Do not inflate 32 pytest functions into 42 by re-labeling predicates. Include this stable inventory in an appropriately noncircular sealed manifest.

### E5A-05 — MEDIUM/HIGH — strict JUnit/fixture identity cross-binding and nested log scanning incomplete (CONFIRMED)

**Contract:** `E05-FC06`, `E05-FC09`; §6.3; §6.4.

`post_seal_verify.py:49–74` checks that JUnit has 32 testcases and no failed/skipped children, that each of 14 expected fixture JSONs exists with `classification=OBSERVED_PASS`, and that all 19 expected case filenames exist. It **does not** verify the exact expected JUnit test function-name set, match individual fixture `source_test` and provenance against JUnit, check each fixture's run/SHA/attempt/approved contract digest, or demand per-fixture semantic negative results. Hashing those 14 JSON files into the auxiliary manifest proves current bytes, not their truth or correspondence to executed tests.

The record-level secret scanner in `harness/evidence.py:204–217,337–340` scans case JSON data recursively, but no source-grounded full scan of **all sealed raw text logs/JUnit/fixture JSONs** is enforced as a mandatory post-seal gate. Independently scanning original artifact bytes for `synth-ci-only`, exposed PostgreSQL DSNs, and configured synthetic secret-sentinel patterns returned **zero matches**. This is an actual-artifact cleanliness observation, not proof the automated redaction boundary rejects all such future leaks.

**Required closure:** exact JUnit 32-function allowlist plus per-fixture source and provider identity check; scanner over all relevant evidence contents with safe non-echoing diagnostics, plus a negative tamper control and process failure.

### E5A-06 — MEDIUM — verifier implementation permits proof inflation in some metadata-only fields (CONFIRMED as design limitation)

`harness/evidence.py:592–608` verifies the root digests' two hex strings, `self_hashed=false`, and `independent_external_verification=PENDING` but **does not independently verify** that `run_id`, `tested_commit_sha`, or `run_attempt` fields of `EVIDENCE_ROOT_DIGESTS.json` equal trusted provider values. The original root record matches the provider-run identity, and this independent review now cross-checks it; nevertheless automated trusted-binding requires that verification on the final path. The primary manifest is byte-verified, but a self-authored digest root is not a cryptographic signature. The post-seal self-report was intentionally excluded from auxiliary manifest to avoid circularity; the provider job outcome is required as the authoritative external terminal check. **No invented self-hash requirement** is suggested.

**Required closure:** compare auxiliary/root identity fields with exact trusted provider event context, and document that provider job state is inspected outside the sealed auxiliary inventory.
