## 4. Material audit findings

### E6A-01 — HIGH — All ten positive `expected_exit_code` values contradict their observed results

**Evidence:** In original `E06_FC_PROOF_MATRIX.json`, for **each** `E05-FC01` … `E05-FC10`:

```json
"positive": { "expected_exit_code": "NONZERO", "observed_exit_code": 0 }
```

The corresponding shared positive receipt `fc_receipts/E05-FC01_positive_shared.json` also has `expected_exit_code="NONZERO"`. This is not only a label issue: it contradicts the contract's required **positive exit 0**. The cause is directly visible in tested `scripts/build_fc_proof_matrix.py:48–66`: `expected_exit_code` becomes `0` only when `side == "positive"`, but the code calls `_receipt("E05-FC01", "positive_shared", ...)` at line 95, so the recorded expectation is `NONZERO` despite observed 0. Tested `harness/evidence.py:674–711` (`validate_fc_proof_matrix`) checks *observed* exit direction and nonempty detector fields, **not `expected_exit_code`**. It therefore reports a schema PASS for a self-contradictory ten-row proof matrix.

**Disposition:** **CONFIRMED / BLOCKING E6-E documentary and machine-readable contract sufficiency**. Correct the receipt-side mapping and enforce exact expected and observed exit semantics in a separately approved future scope. Preserve historic original bytes and the provider success record.

### E6A-02 — HIGH — FC07–FC10 positive process claims do not exercise the corresponding actual acceptance gate

**Evidence:** All **ten** FC positive matrix entries reference `entrypoint="primary_verify_cli"`, the *same* argv and the *same* stdout SHA-256 `03e08a2370085faedf0e9c691d2627252ab2a4b75ed772fb48de3ecc688764bb`. For `FC07` the negative invokes `ci_gate_sequence`; for `FC08`, `FC09` and `FC10` the negative invokes `post_seal_verify`. Tested builder `scripts/build_fc_proof_matrix.py:95, 213–217, 290–295, 342–345, 391–395` copies `clean_pos` with only the detector label changed. The positive status of the **primary** gate is not an independent clean positive for the **CI-equivalent** or **post-seal** gate. `FC08`/`FC10` negatives additionally supply `--skip-matrix-validate 1` and `--reuse-existing-seal 1`; `FC09` supplies `--skip-matrix-validate 1`. These arguments differ from the real successful CI post-seal command, which runs without those options. Disposable synthetic negative branches can validly isolate failures, but their modified options **must not be described as identical to the entire production gate**.

**Disposition:** **CONFIRMED / BLOCKING fully corresponding positive/negative real-gate equivalence**. Record genuine clean positive returns from each relevant actual gate with explicit provenance and explain any necessary isolated negative-only flags; do not treat one primary success as ten different positive gate demonstrations.

### E6A-03 — HIGH — FC matrix validator does not authenticate stated detectors or receipt evidence

**Evidence:** Tested `harness/evidence.py:674–711` checks ten-row IDs, observed return-code direction, nonempty `detector_code`/`entrypoint`, some digests and provider IDs. It does **not** require a strict per-FC expected detector, compare recorded `expected_exit_code` with observed result, validate the associated subprocess receipt JSON against its row, verify output digest from the raw process stream, check `finding_ids` against six specific E5A finding IDs, or enforce the top-level matrix's whole CI provider envelope against trusted data. Tested builder `scripts/build_fc_proof_matrix.py:48–66,97–107` writes the `detector_code` as a caller-supplied constant and sets `finding_ids=["E5A"]`, rather than auditable finding-specific IDs. Independent examination of the 11 preserved stdout files finds meaningful negative errors in each, and their output digests match the matrix; **that supports the observed denials**, but does not turn the present schema validator into a hard detector-to-source proof.

**Disposition:** **CONFIRMED / BLOCKING full FC schema-grounded acceptance claim**. Introduce strict detector-to-output/receipt validation and full provider schema consistency in a future bounded instrument; avoid false claims that no negative errors actually occurred.

### E6A-04 — HIGH — Fixture acceptance is not fully bound to individual fixture origin and lineage

**Evidence:** Tested `scripts/post_seal_verify.py:66–78` checks each E04 fixture's existence, `classification=OBSERVED_PASS`, and (for the actual CI path) only `run_id` and `tested_commit_sha`. It does **not** check that the JSON body's `case_id` equals the expected `E04-Vnn` filename, `source_test` equals the required test function, `run_attempt`, approved `contract_sha256` or `authorization_sha256`, historical lineage, or proof-specific `observed_result` structure. The full `validate_evidence_record` routine in `harness/evidence.py` is invoked for the 19 E03 files by `verify_case_manifest`, but **not** for the 14 fixture records by this loop. An originally observed clean fixture set remains clean; however, a rehashed and re-sealed adversarial fixture with materially inconsistent metadata could evade this fixture-only semantic gate. The E0.6 R0.1 contract, §5 / E5A-05 and `E06-EV05`, requires complete fixture-to-JUnit/provider mapping.

**Disposition:** **CONFIRMED / BLOCKING complete E06-EV05 acceptance coverage**. Validate exact ID, filename, source function, provider envelope, required field types/values and expected negative process receipts for every fixture, then gate the seal on those checks.

### E6A-05 — HIGH/MEDIUM — Post-seal acceptance path still mutates the evidence that it claims to read back

**Evidence:** The normal GitHub workflow calls `scripts/post_seal_verify.py` with no CLI options. Tested `post_seal_verify.py:87–107` then **calls `write_auxiliary_manifest(...)` and `write_root_digests(...)`** before verifying them, and at line 140 writes a status JSON. Tested `harness/evidence.py:504–530` assembles the expected inventory from a base list plus only `fc_receipts/*.json` (not the `.stdout.txt` receipts), then writes the auxiliary manifest. Tested `post_seal_verify.py:109` verifies the newly written manifest against the **same dynamically generated inventory** rather than a separately frozen expected inventory. This combines sealing and verification within one process. It cannot, by itself, prove that an independently established seal was immutable **before** final acceptance. The optional `--reuse-existing-seal 1` path is closer to read-back mode, but is not used by successful CI, and even that path writes the excluded `POST_SEAL_VERIFIER.json` status. The R0.1 contract §9 explicitly distinguishes the *aux manifest finalization* phase from a *read-only post-seal mandatory gate*.

**Disposition:** **CONFIRMED / BLOCKING the literal sequencing/read-only acceptance claim**. Separate seal creation from an independent, no-write read-back gate, enforce an exact predeclared inventory (or explicitly signed fully enumerated policy), and treat later status files as unsealed outputs rather than asserting complete immutability.

### E6A-06 — MEDIUM — E06-EV01..EV06 closure judgment sidecar is absent from the original CI artifact

**Evidence:** Cursor's final report references `evidence/E06_EV_CLOSURE_JUDGMENTS.json`. That file exists in the **final evidence-only Git commit** `36a0cebc...` (Git blob `77cd73980bb7012daa03326410a551de050bfdbc`) but is **absent** from the original provider artifact's 75 files and absent from its 35-entry auxiliary manifest. Its six `CLOSED_BY_SELF_VERIFIER` statements therefore are **post-CI assertions**, not original provider-sealed E06 closure output. The E0.6 contract §10 distinguishes `SELF_TESTED` from `INDEPENDENTLY_VERIFIED`; the final sidecar uses a different `CLOSED_BY_SELF_VERIFIER` label. This does not contradict the genuinely positive FC receipts; it restricts what the closure sidecar can establish as immutable CI evidence.

**Disposition:** **CONFIRMED / LIMITED GOVERNANCE PROVENANCE**. Require six explicit self-tested closure verdicts tied to original provider evidence and the contract's approved status vocabulary, or classify the current sidecar correctly as final-report commentary rather than sealed/tested acceptance material.

### E6A-07 — MEDIUM / DOCUMENTATION BOUNDARY — Direct auxiliary inventory omits stable accepted process-text evidence

**Evidence:** Original artifact has 11 `fc_receipts/*.stdout.txt` files and a stable `fc_matrix_builder.txt`, none directly enumerated among 35 aux entries. Original `harness/evidence.py:504–530` dynamically includes only `fc_receipts/*.json`. The contract §9 demands an exact, declared auxiliary evidence inventory covering stable required output/receipt material; `stdout` streams are used in FC detector arguments. Crucially, **all 11 stdout+stderr digests are independently reproducible** from the text files and their hash is recorded inside the already-sealed matrix; thus an **indirect** integrity chain exists in this original artifact. The issue is direct inventory completeness and explicit receipt schema handling, **not evidence that stdout files changed or lack all cryptographic authentication**.

**Disposition:** **CONFIRMED DIRECT INVENTORY GAP, mitigated by 11/11 indirect hash matches**. Formalize whether direct entries are mandatory or explicitly allow a fully verified transitively sealed receipt layer. Scan any included text for redaction, including unsealed reports/diagnostics as the policy requires.
